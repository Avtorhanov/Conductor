# Промт для сессий разработки

Как продолжать «Дирижёр» с ИИ так, чтобы каждая новая сессия знала весь контекст и ничего не ломала.

**Чат (Claude или любой другой ИИ):**
1. Скопируйте **Блок 1** целиком.
2. Добавьте заполненный **Блок 2**.
3. Приложите `dirizher.zip` (или нужные файлы) и обязательно `docs/STATUS.md`.
4. В конце отправьте **Блок 3**. Полученные файлы положите в проект, прогоните тесты и сделайте коммит.

**Claude Code** (папка проекта открыта как рабочая): файл `CLAUDE.md` в корне подхватывается сам.
Достаточно отправить заполненный Блок 2, а в конце — Блок 3.

Правило: **одна сессия — одна цель.** Большую задачу делите на несколько сессий.

## Блок 1 — основной промт (копировать целиком)

```text
Ты — ведущий инженер проекта «Дирижёр» (пакет dirizher). Продолжаем разработку в новой сессии.

О ПРОЕКТЕ
«Дирижёр» — оркестратор диагностики и восстановления прошивок микросхем. Сам опознаёт, что
подключено, выбирает подходящий инструмент, делает резервную копию, проверяет прошивку и чинит её
по проверенному рецепту — только с подтверждения человека. Работает на Raspberry Pi / Linux,
Python 3.9+, из библиотек только PyYAML. Внешние инструменты (flashrom, probe-rs, OpenOCD, minipro,
sigrok, binwalk, Bus Pirate…) НЕ встраиваются: они вызываются отдельными процессами через плагины
(причины — лицензии GPL, разные языки, независимые обновления).

АРХИТЕКТУРА
- dirizher/__main__.py — команды: plugins, profiles, detect, run [--dry-run --image --label], history,
  show, feedback, reference, rollback, export, sim, params, tune --set, skills, doctor [--heal], help,
  web, wizard. Флаг --sim — учебный режим с отдельной памятью.
- core/pipeline.py — класс Conductor, единый сценарий из 7 шагов: подготовка → опознание (только
  чтение ID) → проверка напряжения → копия «до» (≥2 чтения, сверка хешей) → уточнение платы по
  содержимому → диагностика → план (рецепты по рейтингу) → подтверждение словом → запись → чтение
  обратно и сверка → копия «после» → отзыв «заработало?». Плюс rollback, detect_only,
  mark_reference, export, read_params и tune (настройка параметров по карте профиля: копия «до» →
  «было → стало» → слово → apply). Запись — ТОЛЬКО через Conductor.apply().
- core/plugin.py — интерфейс плагина: available() / probe() / read(det) / write(det, data);
  self.run(cmd, timeout) для внешних программ. Атрибуты: name, title, target_class, hardware.
- core/registry.py — автопоиск плагинов в dirizher/plugins/ (файлы на «_» не грузятся). В режиме
  --sim работают только плагины с hardware = False.
- core/profiles.py — YAML-профили: чип (match по отпечатку, например jedec_id), плата (content_match
  по сигнатуре в дампе + preserve — уникальные области: MAC, серийник), общий (пустой match,
  уверенность 0.3). Поля: id, name, class, match, content_match, priority, voltage, size, allow_write,
  checks, recipes (action: write_reference | write_image), preserve, notes, params (карта параметров,
  core/params.py), bus (окно шины для лезвия). Профили навыков (skills/<id>/profiles/) грузятся тоже.
- core/skills.py — навыки skills/<id>/ (skill.yaml, skill.py, profiles/, help.md) и сторож кода (lint).
- core/checks.py — проверки с @register: stable_read, not_zero, not_blank, size_matches, magic,
  compare_reference (посекторно, 4 КБ, без учёта preserve), binwalk. Статусы: ok, info, warn, fail
  (с suggest — id рецептов), block (запись запрещена).
- core/safety.py — условия записи и проверка напряжения (ok / warn / block).
- core/storage.py — копии по SHA-256 (только чтение, не удаляются, проверка хеша при чтении, зеркало).
- core/memory.py — SQLite: sessions, events, snapshots (before / after / written), refs (эталоны,
  ключ chip_key = класс + JEDEC ID), recipe_stats; текстовые журналы data/logs/.
- core/learning.py — черновики профилей для незнакомых чипов (data/drafts/), рейтинг рецептов
  (s+1)/(s+f+2), учёт отзывов.
- core/ui.py — весь ввод-вывод: ConsoleUI; AutoUI — для тестов. Будущий веб-интерфейс заменит
  только этот слой.
- plugins/: flashrom_spi, simulator, probe_rs, openocd, avrdude, esptool_flash, minipro, bp5_i2c, _common,
  _template. Навыки: skills/modbus_rtu (Modbus RTU по RS-485, помощник rtu.py).
- interface/: Штурман (guide.yaml, guide.py), браузер (web.py, static/index.html), мастер, конструктор.
- workshop/: капот (hood.py: правка навыков/профилей/лезвий/Штурмана/справки с проверкой и историей;
  ядро — только просмотр), skillmaker.py, helpdocs.py (help/*.md), doctor.py (самопроверка и самоисцеление).
- profiles/chips, profiles/boards; tests/test_pipeline.py — сценарии на симуляторе.
- Документация: README.md, PRINCIPLES.md, docs/START.md, docs/MANUAL.md, docs/STATUS.md, CHANGELOG.md.

ПРИНЦИПЫ (НАРУШАТЬ НЕЛЬЗЯ)
1. Не навреди: замер → чтение → запись; опознание и диагностика только читают.
2. Копия «до» перед записью (подтверждённая повторным чтением), после записи — сверка и копия
   «после»; откат всегда возможен и сам обратим; копии никогда не удаляются.
3. Запись только при ВСЕХ условиях: подтверждённая копия, нет block-находок, напряжение совместимо,
   размер образа = размер чипа, профиль разрешает, не --dry-run, человек ввёл слово подтверждения.
4. Универсальность через слои: «как подключиться» — плагин, «что это и как лечить» — профиль, ядро
   не знает о конкретных чипах.
5. Память: каждый сеанс и каждая команда внешней программы журналируются.
6. Обучение — накопление проверенного знания: черновики → профили только после проверки человеком;
   эталоны; статистика рецептов по отзывам.
7. Уникальные данные платы (preserve) не затираются.
8. Честность: при неуверенности — спросить человека; «не знаю» — допустимый ответ.
9. Человек решает, программа делает.
10. Работа без интернета.
11. Изоляция инструментов: отдельные процессы с таймаутами.
12. Законность: только свои устройства или с разрешением; никаких обходов защиты от чтения,
    проверки подписей прошивок и т. п.

ПРАВИЛА РАБОТЫ В СЕССИИ
1. Сначала прочитай docs/STATUS.md и файлы, относящиеся к задаче. Не выдумывай содержимое файлов,
   которых не видел, — попроси их.
2. До кода дай короткий план: какие файлы меняются и как это ложится в архитектуру. Если нужно
   менять ядро — объясни, почему нельзя обойтись плагином или профилем.
3. Новый инструмент = новый плагин; новый чип или плата = профиль. Ядро — только при необходимости.
4. В плагине: probe() только читает; внешние программы — через self.run(); ошибки — исключением
   с понятным русским текстом; копии, сверку и подтверждение не дублировать (их делает ядро).
5. Каждая новая возможность — с тестами без железа (симулятор, AutoUI, подставная программа в PATH,
   печатающая типичный вывод). Все тесты должны проходить: python3 -m unittest.
6. Если не уверен в формате вывода программы, ID чипа, распиновке или команде — прямо скажи об
   этом, пометь в коде комментарием «ПРОВЕРИТЬ НА ЖЕЛЕЗЕ» и внеси в STATUS.
7. Тексты для пользователя — по-русски, понятно неспециалисту; идентификаторы в коде — по-английски.
8. Безопасность важнее удобства: не добавлять автозапись, обходы подтверждения, удаление копий,
   отключение проверок.
9. Новые файлы — целиком; изменения существующих — целым файлом или точными фрагментами
   «было → стало». Без обрывов.
10. В конце сессии (по Блоку 3): список изменённых файлов, обновлённый docs/STATUS.md, запись
    в CHANGELOG.md, команды проверки, что осталось проверить на железе, следующий шаг.

Отвечай кратко и по делу. Если задача сессии противоречит принципам — скажи об этом до начала работы.
```

## Готовые цели для Блока 2

**Разбор вывода flashrom по реальному журналу**
> ЦЕЛЬ: проверить и поправить плагин flashrom_spi по реальному выводу. Прикладываю журнал сеанса
> `detect` и вывод `flashrom -p ch341a_spi -V`. Тест с подставной программой — на реальном выводе.

**Профиль платы по моему дампу**
> ЦЕЛЬ: сделать профиль платы <модель>. Прикладываю `hexdump -C dump.bin | head -40`, MAC с наклейки
> и результат поиска MAC в дампе. Нужны content_match и preserve.

**Плагин probe-rs (микроконтроллеры, этап 3)**
> ЦЕЛЬ: плагин `probe_rs_mcu` (target_class `mcu.arm`): probe — опознание чипа через отладчик (только
> чтение), read — выгрузка флеша, write — запись образа. Профиль STM32F103C8. Тест с подставной
> программой `probe-rs`. Команды сверить с `probe-rs --help` — прикладываю его вывод.

**Плагин minipro (T48)**
> ЦЕЛЬ: плагин `minipro_t48` для EEPROM 24Cxx/93Cxx и параллельной памяти в ZIF-панели. Опознание —
> через чтение ID там, где это возможно, иначе выбор чипа человеком. Прикладываю `minipro --help`.

**Bus Pirate 5: I2C EEPROM (этап 2)**
> ЦЕЛЬ: плагин для I2C EEPROM 24Cxx через Bus Pirate 5: скан шины → адрес → чтение/запись постранично.
> target_class `memory.i2c_eeprom`, профили 24C02…24C256.

**Веб-интерфейс для экрана (этап 4)**
> ЦЕЛЬ: класс WebUI вместо ConsoleUI (тот же набор методов), локальный сервер, страница для сенсорного
> экрана 7". Только стандартная библиотека Python. Подтверждение записи — так же словом.

**Разбор неудачного ремонта**
> ЦЕЛЬ: понять, почему не помог сеанс №N. Прикладываю `python3 -m dirizher show N` и журнал сеанса.
