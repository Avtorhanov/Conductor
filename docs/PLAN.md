# План 0.7.0 «Порядок и универсальность»

Разобран и согласован в сессии 2026-11-25 (журнал — `docs/STATUS.md`). Работа идёт **цепочкой сессий
Claude Code**: каждая делает один раздел ниже, начиная с результата предыдущей. Сессию запускает и
принимает сессия-координатор; люди к ним не подключены.

Цели:
1. **Удобство** — у каждой возможности одно место; человек начинает с того, что у него в руках;
   настройки — формой, а не правкой YAML.
2. **Ясность** — у каждого знания один источник; ошибка объясняет, что делать, и ведёт на карточку.
3. **Универсальность** — общие механизмы (схема настроек, `inspect()`, карта разделов) важнее новых лезвий.
4. **Раскрыть движки** — их диагностику только чтением, а не одни read/write.
5. **Надёжность** — каждый прогон на железе становится тестом; замер важнее заявления.

## Общие правила для каждой сессии

- В начале прочитай `CLAUDE.md`, `docs/STATUS.md`, этот файл (раздел «Общие правила» и свой раздел).
  Остальное читай по необходимости и кусками: `index.html` 2400 строк, `playground.yaml` 1400 строк.
- **Человека нет — вопросов не задавай.** Принимай разумное решение, записывай его в STATUS
  («Принятые решения» или «Открытые вопросы») и в отчёт.
- Только свой раздел. Не переделывай соседнее «заодно». Что заметил вне раздела — в отчёт.
- Принципы (`PRINCIPLES.md`) и жёсткие правила `CLAUDE.md` — без исключений: `probe()` и `inspect()` только
  читают; запись — только через `Conductor.apply()`; обходов подтверждения нет; защиту чтения не снимаем.
- Ядро меняется, только если иначе нельзя; в STATUS («Принятые решения») — что изменено и почему.
  Прежние сценарии и ответы ядра — как были.
- Всё непроверенное на железе — `ПРОВЕРИТЬ НА ЖЕЛЕЗЕ` в коде и пункт в STATUS «Проверить на железе».
- Тексты для человека — по-русски, простыми словами; идентификаторы — по-английски. Python 3.9+, только PyYAML.
- **Тесты:** каждая новая возможность — с тестом без железа (симулятор, `AutoUI`, подставная программа
  в `tests/fakes/fake_tools.py`, эмулятор на pty). В конце — весь набор `python3 -m unittest` (около 2 минут),
  должен пройти целиком. Смысл прежних тестов не менять; если тест пришлось поправить — объяснить в коммите.
- Подводные камни:
  - «сеансы вживую» в `playground.yaml` сверяются с выводом ядра (`tests/test_playground.py`) — изменил текст
    ядра, обнови строки тренажёра;
  - `AutoUI` отвечает по списку: новый вопрос в сценарии (например, выбор из двух рецептов) сдвигает ответы
    в тестах;
  - демо `tools/build_pages.py` записывает ходы ядра — после изменений сценария запусти `--quick`,
    чтобы убедиться, что сборка не падает;
  - `fingerprint` сравнивается при откате — не добавляй туда то, что меняется между запусками (версии программ, замеры).
- Версия пакета — `0.7.0` (ставит S1). `CHANGELOG.md` — одна секция «## 0.7.0 — в работе», каждая сессия
  дописывает свой подраздел. `docs/STATUS.md` — как требует `CLAUDE.md`, строка в журнал сессий.
- Коммит с понятным сообщением; пуш в свою ветку (её задаёт координатор). Без PR, `main` не трогать.
- **Отчёт координатору** — коротко, через `send_message` (адрес — в запросе сессии): ветка, последний
  коммит, тесты (сколько, все ли прошли), что сделано, что нет и почему, что проверить на железе.

## S1. Журнал → тест, версия программы (Opus)

Зачем: разбор вывода программ не проверен на железе. Первый же прогон должен стать постоянным тестом,
а человек без ПК должен суметь передать журнал с телефона.

1. **Полный вывод команд.** Сейчас `Runner` кладёт в событие хвост 3000 символов, а файл журнала — 1500.
   У `flashrom -V` нужная строка RDID может оказаться раньше хвоста. Сохраняй полный stdout/stderr каждой
   команды (до 1 МБ на поток) отдельными файлами рядом с журналом сеанса (`data/logs/session_NNNNN/…`).
   Дампы туда не попадают никогда (`read` пишет во временные файлы — их не трогать).
2. **`Plugin.version()`** → строка или `None` (по умолчанию `None`). Реализуй для flashrom, probe-rs,
   OpenOCD, minipro, avrdude, esptool (уже определяет версию), симулятора. Ядро вызывает её один раз
   за сеанс после опознания и пишет событие «инструмент: … версия …». **Не в fingerprint.**
   Точную команду версии каждой программы — `ПРОВЕРИТЬ НА ЖЕЛЕЗЕ`.
3. **Пакет журнала для разработки** (без дампов): команды, коды возврата, полный вывод, версии, отпечаток,
   итог сеанса. Перед выдачей — очистка: MAC → `02:00:00:xx:xx:xx`, серийные номера и «Serial code»,
   имя хоста, домашние пути. CLI: `python3 -m dirizher journal N --to файл.json`. Веб: «Журнал» → сеанс →
   «Скачать журнал для разработки» (с телефона: прибор работает, телефон скачивает файл).
4. **`tools/log_to_test.py пакет.json`** → фикстура `tests/fixtures/real/<программа>_<версия>_<n>.json`
   (команда, код, вывод) и ожидаемый результат разбора (опознание: класс, jedec_id/name/size и т. п.).
   Общий тест `tests/test_real_outputs.py` прогоняет каждую фикстуру через настоящий плагин с подменённым
   `Runner` (повтор записанных ответов по команде). Пока фикстур нет — тест проверяет себя на одной
   синтетической фикстуре, помеченной как синтетическая.
5. Справка: короткая статья `help/journal.md` «Журнал для разработки: как передать прогон с железа».

Готово, когда: полный вывод хранится; версия видна в журнале сеанса; пакет без MAC и серийников
(тест); фикстура из пакета проходит через плагин (тест); кнопка в вебе работает.

## S2a. Схема настроек лезвий, форма в «Прибор» (Opus)

Зачем: чтобы включить лезвие, сейчас нужно руками скопировать секцию в `config.yaml` на приборе,
а в капоте `config.yaml` открыт только для просмотра. С телефона это невозможно.

1. **`Plugin.settings_schema`** — список полей: `key`, `title`, `type` (str, int, float, bool, choice,
   list, port, path), `required`, `default`, `example`, `help`, `choices`, `safety` (`voltage` — поле
   влияет на напряжение). Заполни для всех встроенных лезвий и лезвия навыка `modbus_rtu`.
   Общие поля (`enabled`, `programmer_voltage`, `extra_args`, таймауты) — один раз в базовом классе.
2. **Проверка по схеме** при загрузке: неизвестный ключ (опечатка `flash_sise`) — предупреждение
   в самопроверке и в отчёте плагинов; нет обязательного поля — «недоступен: укажите <название поля>»;
   неверный тип — понятное сообщение. Логика `available()` лезвий остаётся.
3. **Файл настроек инструментов** `config.tools.yaml` рядом с `config.yaml` (в `.gitignore`): секция
   `plugins:`, читается после `config.yaml` и перекрывает его. `config.yaml` по-прежнему не правится
   программой. Сохранение — через капот (`Hood`): проверка по схеме, история версий, слово «ДА»
   (настройки влияют на железо), только при открытом капоте (экран прибора или `hood.edit: true`).
4. **Форма в вебе:** «Прибор» → «Инструменты» → лезвие → «Настроить». Поля по схеме, текущее значение
   и откуда оно (config.yaml / config.tools.yaml / по умолчанию), подсказка и пример. Поле с
   `safety: voltage` выделено и с предупреждением. «Проверить» (без записи) и «Сохранить» (слово «ДА»).
   После сохранения — статус лезвия заново. То же в мастере терминала (поле за полем) и CLI
   `python3 -m dirizher tool <имя> [--set ключ=значение]`.
5. Самопроверка: оба лезвия `probe_rs` и `openocd` включены — предупреждение (конфликт на одном МК).
6. `docs/config-snippet-0.3.0.yaml` — тест, что его ключи есть в схемах.

Готово, когда: лезвие включается и настраивается с экрана без правки `config.yaml` (тест через HTTP);
опечатка в ключе видна в самопроверке; напряжение без слова «ДА» не меняется (тест).

## S2b. Модель цели из профиля, «начать с переходника» (Opus)

Зачем: модель МК (`chip`, `part`, `device`, `eeprom`) и размеры (`flash_size`) сейчас вписаны в настройки
лезвия и повторяют `size` профиля; при смене платы снова правится config. Начинать стоит с того, что у
человека в руках, — с переходника.

1. **Поле профиля `tool:`** — настройки лезвий для этой модели, например у `stm32f103c8`:
   `tool: {probe_rs: {chip: STM32F103C8, flash_base: 0x08000000}, openocd: {target: target/stm32f1x.cfg, mcu: STM32F103C8}}`;
   размер берётся из `size`. Заполни у `stm32f103c8`, `atmega328p`, `esp32_4mb`, `eeprom_24c02`.
   Проверка поля по схеме лезвия (S2a).
2. **Выбор модели перед сеансом.** Параметр `target` (id профиля) у `run`, `detect`, `params`, `tune`:
   настройки лезвия = config.yaml < config.tools.yaml < `profile.tool[лезвие]`. Где модель не узнаётся
   по ID (ARM, AVR, 24Cxx), Штурман спрашивает её списком профилей нужного класса. Последний выбор
   запоминается как удобство. Уверенность опознания по-прежнему честная (модель из выбора человека).
3. **«Подключить инструмент» начинается с переходника.** Штурман → выбрать карточку переходника → список
   проверок, каждая со статусом и советом: программа установлена (`shutil.which`); правило udev на месте
   (`/etc/udev/rules.d/99-dirizher*.rules`); пользователь в `plugdev`/`dialout`; устройство видно по USB
   (VID:PID карточки в `/sys/bus/usb/devices/*/idVendor|idProduct` — только stdlib); лезвие включено и
   настроено (S2a) → «Настроить» → «Проверить подключение» (опознание только лезвиями этого переходника).
4. **Опрос только нужных лезвий.** Если переходник выбран — `detect` опрашивает только его лезвия
   (сейчас — все включённые по очереди, с долгими таймаутами).
5. **Подготовка по переходнику.** Строки шага 1 «Подготовка» (`PREFLIGHT`) — из карточки переходника
   (поле `preflight:`) или лезвия; общий текст — запасной. Сейчас про прищепку говорится даже для ESP и Modbus.

Готово, когда: STM32 и ATmega выбираются из списка без правки config (тест); `detect` с выбранным
переходником зовёт только его лезвия (тест); проверки подключения отдают понятные статусы (тест с
подменённым `/sys` и PATH); подготовка у ESP без слов о прищепке.

## S3. `inspect()` и замер напряжения (Opus)

Зачем: движки умеют больше, чем read/write. И напряжение сейчас сверяется с вписанным в настройки,
а не с замеренным, хотя ST-Link (через OpenOCD) меряет питание цели.

1. **`Plugin.inspect(det)`** — только чтение, по умолчанию пусто. Возвращает находки (`Finding`) и, если
   есть, `measured_voltage`. Ядро вызывает после опознания, до шага напряжения; находки показываются
   и пишутся в журнал; находка `block` запрещает запись (как диагностика).
2. Что открыть (каждое — с подставной программой в `fake_tools.py`, формат — `ПРОВЕРИТЬ НА ЖЕЛЕЗЕ`):
   - flashrom: состояние защиты записи (`--wp-status`, если версия умеет) — объясняет «записалось, но не изменилось»;
   - OpenOCD: замеренное напряжение цели (уже разбирается, но идёт только в описание); состояние защиты
     чтения, если для цели есть команда только чтения;
   - probe-rs: чтение регистра ID (адрес — в профиле, поле `id_register` + ожидаемое значение) —
     подтверждает модель, выбранную человеком;
   - avrdude: чтение фьюзов и lock-битов (только чтение, вывод в stdout) и расшифровка по данным профиля
     (`fuses:`) — кварц, BOD, защита. Запись фьюзов по-прежнему запрещена;
   - esptool: MAC и ID; если установлен `espefuse` — сводка (только чтение): шифрование флеша, secure boot;
   - minipro: проверка контакта выводов, если программа умеет (флаг — `ПРОВЕРИТЬ`);
   - Bus Pirate 5: замер напряжения на VOUT, если прошивка его показывает.
3. **Замер в шаге 3.** Если `measured_voltage` есть: расхождение с напряжением профиля больше допуска —
   стоп с понятным текстом («замерено 1,8 В, а профиль на 3,3 В»). Замер никогда не ослабляет прежние
   проверки, только добавляет. Нет замера — всё как раньше.
4. Карточки движков: в «Как работает в Дирижёре» — что Дирижёр берёт у программы для диагностики.

Готово, когда: замер 1,8 В при профиле 3,3 В останавливает сеанс (тест); фьюзы ATmega видны в
диагностике по-русски (тест); защита записи flashrom видна (тест); старые сценарии не изменились.

## S4a. Карта разделов и частичное восстановление (Opus)

Зачем: «отличается 157 секторов» мало что говорит. Профиль должен знать разделы: загрузчик, ядро,
файловая система, настройки, калибровки, MAC.

1. **`core/layout.py`** по образцу `core/params.py`: поле профиля `layout:` — разделы `id`, `title`,
   `offset`, `length` (или `end`), `kind` (boot, kernel, rootfs, config, calibration, unique, data, free),
   `preserve` (уникальное), `restore` (можно ли брать из эталона). Проверка: без пересечений, в пределах `size`.
2. `preserve` профиля дополняется разделами с `preserve: true` (старое поле работает как раньше).
3. **Диагностика по разделам:** сравнение с эталоном называет разделы («отличается: «ядро» — 12 секторов»),
   пустой раздел загрузчика — находка. Без `layout` — как раньше.
4. **Рецепт `restore_regions`** (новое действие ядра `write_reference_regions`): образ = текущий чип,
   а повреждённые восстанавливаемые разделы — из эталона. Защита та же: копия «до», план с перечнем
   разделов, «ДА», сверка всего чипа, копия «после». Объяснить изменение ядра в STATUS.
5. Карта у `example_sim_board` (заголовок, данные, параметры, MAC и серийник) — чтобы учебный режим
   и демо её показывали. Учти подводные камни: выбор из двух рецептов сдвигает ответы `AutoUI`,
   «сеансы вживую» в тренажёре, демо.
6. Веб и мастер: в подробностях сеанса — разделы с отличиями.

Готово, когда: учебная порча называет раздел; `restore_regions` чинит только повреждённое, а
испорченное вне разделов «restore» не трогает (тест); старые профили без `layout` работают как раньше.

## S4b. Разделы сами: таблица ESP, Intel IFD, черновик платы (Opus)

1. **Определители разметки** (`core/layout_detect.py`, регистрация как у проверок): по содержимому дампа
   строят `layout`, если в профиле его нет. Только stdlib.
   - таблица разделов ESP32 (0x8000, записи по 32 байта, магия `AA 50`, запись MD5 `EB EB`): nvs и
     phy_init → `preserve`; app, otadata — по типам. Снимает пометку «добавьте preserve вручную» в `esp32_4mb`;
   - Intel Flash Descriptor (подпись `5A A5 F0 0F` по смещению 0x10, FLMAP0 → регионы): Descriptor, BIOS,
     ME, GbE (MAC — `preserve`), Platform Data. Для ноутбуков (маршрут Acer в тренажёре).
   Формат каждого — по документации; на настоящих дампах — `ПРОВЕРИТЬ НА ЖЕЛЕЗЕ`.
2. Профиль может перечислить определители (`layout_auto: [esp_partitions]`); общий SPI-профиль пробует
   известные подписи.
3. **Черновик профиля платы при сохранении эталона:** `content_match` (подпись в начале дампа) и, если
   установлен binwalk, `binwalk_expect` из найденных сигнатур — в `data/drafts/`, как черновики чипов.
4. Тесты: синтетические образы с правильной таблицей ESP и IFD; испорченная таблица — понятная находка,
   а не падение.

## S5. Новые лезвия (Opus)

Пиши сразу по новым правилам (схема настроек S2a, `inspect()` S3, `tool:` в профилях S2b).
Порядок — по пользе; не успеваешь всё — сделай первые хорошо и опиши остальное в отчёте.

1. **`pi_i2c`** — EEPROM 24Cxx через I2C самого Raspberry Pi (`/dev/i2c-1`), без покупок. Помощник-процесс
   `dirizher/helpers/i2c_eeprom.py` на stdlib (`fcntl.ioctl` I2C_SLAVE / I2C_RDWR, при необходимости
   `ctypes`): чтение, запись страницами с ожиданием цикла записи, только изменившиеся куски. Транспорт
   отделён от логики — в тестах подменяется эмулятором EEPROM. Напряжение 3,3 В (логика Pi).
   Карточка `rpi_i2c` (собрать): провода — выводы 3 SDA, 5 SCL, 1 3,3 В, 6 GND; `raspi-config` → I2C.
2. **Журнал загрузки по UART** — `dirizher/extras/uart.py` по образцу `extras/sigrok.py`: только приём,
   ничего не отправлять; запись в `data/captures/`, сеанс в журнале; подбор скорости по доле печатных
   символов (по желанию). Действие Штурмана, веб и мастер. Тест — эмулятор на pty, печатающий
   журнал загрузки в стиле U-Boot.
3. **CH341A в режиме I2C** — только если найдётся сопровождаемая открытая программа с понятной командной
   строкой (проверь поиском, например ch341eeprom). Есть — лезвие с подставной программой, всё
   `ПРОВЕРИТЬ НА ЖЕЛЕЗЕ`. Нет уверенности — не выдумывай: запись в STATUS «Открытые вопросы».
4. Профили 24C04…24C512 (по одному общему шаблону через `tool:` или отдельные — на твоё усмотрение).
