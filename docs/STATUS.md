# Состояние проекта

Этот файл обновляется в конце каждой сессии разработки и прикладывается к началу следующей.

**Версия:** 0.5.0
**Этап:** 1 — ядро и SPI-память (код готов; идёт проверка на железе) + интерфейсы (код готов, проверен в браузере на симуляторе) + лезвия этапов 2–3 (код готов, проверен на подставных программах, ждёт железа) + **мастерская** (код готов, проверен на симуляторе, эмуляторе Modbus и в браузере) + **справочник и демо на GitHub Pages** (код готов, проверен в Chrome; демо собрано и пройдено в браузере локально, на GitHub ещё не опубликовано)

4. Свои профили: 3 чипа + 1 плата — через конструктор профиля (START.md, день 3). На эталоне попробовать `binwalk_expect`.
5. Этап 2: Bus Pirate 5 — включить `bp5_i2c` (docs/config-snippet-0.3.0.yaml), пройти чек-лист «Проверить на железе».

## Принятые решения
- Движки (flashrom, probe-rs и др.) не встраиваются, а вызываются отдельными процессами: лицензии GPL, разные языки, независимые обновления.
- У симулятора отдельная память (`data/simulator/`), чтобы учебные эталоны не смешивались с настоящими.
- Эталоны ищутся по ключу чипа (класс + JEDEC ID). Эталон с другого профиля — только после подтверждения человеком.
- При восстановлении области `preserve` берутся с текущего чипа. Если они пусты — предупреждение.
- Интерфейсы — отдельный слой `interface/`. Все экраны берут вопросы и подсказки из одного Штурмана.
- Веб — только стандартная библиотека Python (без Flask и CDN): работает офлайн, ставить нечего.
- «Отмена» на экране = безопасный ответ ядру (как пустой ввод в консоли); на паузе перед началом — прерывание сеанса.
- Слово подтверждения вводится вручную и проверяется на сервере; кнопкой не заменяется.
- Профиль из конструктора включается только после галочки «сверил с даташитом» и с указанным напряжением; файлы не перезаписываются.
- (0.3.0) Напряжение адаптера задаётся у каждого плагина: USBasp 5 В, CH341A 3.3 В, BP5 регулируемый.
- (0.3.0) Bus Pirate 5 управляется через помощника-процесс на stdlib (termios), а не через pyserial в ядре.
- (0.3.0) AVR: образ = flash + EEPROM. Фьюзы и lock-биты не читаются в образ и никогда не пишутся.
- (0.3.0) Модель МК для probe-rs/OpenOCD и модель 24Cxx задаёт человек; уверенность 0.7–0.75.
- (0.3.0) Опасные параметры отклоняются до запуска программы, даже если вписаны в extra_args.
- (0.3.0) minipro не обслуживает микроконтроллеры — для AVR есть avrdude.
- (0.3.0) sigrok-cli — не лезвие, а отдельный модуль `dirizher.extras.sigrok`.
- (0.3.2) Тема «Нави» заменила тёмную (не третья тема): меньше вариантов для проверки. Сохранённое «dark»
  открывается как «Нави». Форма и объём заданы переменными CSS; светлая тема их обнуляет и выглядит как раньше.
- (0.3.2) Шрифты не загружаются из сети и не раздаются `web.py`: заголовки берут Exo 2, только если он установлен.
- (0.4.0) Универсальность — через **карту параметров**, а не через код под каждый прибор: параметр = типизированное
  поле в образе памяти. Одинаково для EEPROM, блока конфигурации во флеше и регистров Modbus. Запись параметров —
  тот же путь, что и любая запись (копия «до», сверка, «ДА», копия «после»).
- (0.4.0) Изменение ядра: добавлены `tune/read_params`, загрузка навыков, `voltage_check`, таблица `fixes`,
  `health/repair` хранилища. Без этого параметры, навыки и самоисцеление не встраиваются в общую защиту;
  прежние сценарии и тесты не тронуты.
- (0.4.0) Капот правит только то, что расширяет Дирижёр. Ядро, `config.yaml`, сторож лезвий, симулятор и
  интерфейсы — только просмотр: в них защита и эталоны тестов, их меняют через git с тестами.
- (0.4.0) Капот закрыт по умолчанию: правка кода = выполнение кода на приборе. Открыть — физически с экрана
  прибора (до перезапуска) или `hood.edit: true`; с телефона открыть нельзя. Код и профили — со словом «ДА».
- (0.4.0) Сторож кода — не песочница: ловит ошибки (удаление файлов, процессы мимо `self.run()`, eval/exec,
  запись из `probe()`, доступ к хранилищу копий), а не злой умысел. Пробный импорт — отдельным процессом.
- (0.4.0) Самоисцеление чинит только доказуемое: копию — из места, где SHA-256 сходится; правку — версией
  из истории, которая проходит проверку. Только по кнопке человека или `doctor --heal`. Ничего не удаляется:
  испорченное — в карантин, прежние версии — в историю.
- (0.4.0) Самообучение — «что помогло» словами человека, с счётчиком подтверждений; без догадок и автодействий.
- (0.4.0) Modbus RTU — помощник-процесс на stdlib (как BP5); прибор = окно регистров настроек; модель задаёт
  человек; адрес и скорость в учебной карте — только чтение (после их смены сверка по старому адресу невозможна).
- (0.4.0) Окно чтения Modbus — только регистры настроек: живые величины ломают сверку повторных чтений,
  и запись блокируется (проверено тестом).

- (0.5.0) Справочник — не код, а данные: карточки YAML в `catalog/`, рисунки описаны данными и рисуются
  интерфейсом (SVG без картинок и сети). Новый переходник или движок — новая карточка, ядро не меняется.
- (0.5.0) Карточки только описывают — правятся в капоте без слова «ДА», но с той же проверкой, что при загрузке.
- (0.5.0) Авторы движков обязательны (самопроверка напоминает): справочник отдаёт должное открытым проектам,
  на которых стоит Дирижёр. Сведения об авторах — из man-страниц, сайтов и репозиториев проектов.
- (0.5.0) Демо на GitHub Pages — та же страница плюс подмена связи; ходы записывает настоящее ядро на симуляторе,
  а не отдельная имитация в JS. Поэтому демо не расходится с прибором: меняется ядро или Штурман — меняется демо.
- (0.5.0) Ядро не менялось. Изменены только слой интерфейсов и мастерская (web, index.html, guide, wizard,
  hood, doctor, helpdocs, skillmaker, `__main__`).

## Открытые вопросы
- Публиковать демо только из `main` или из любой ветки (тогда нужна своя среда `github-pages` без защиты ветки)?
- Форм-фактор: Raspberry Pi 5 + сенсорный 7" или ноутбук? (интерфейс готов к обоим)
- Какие устройства чинить в первую очередь (определяет порядок профилей и включения лезвий)?
- Нужен ли постоянный код доступа по умолчанию или случайный при каждом запуске (сейчас — случайный)?
- Нужен ли второй транспорт для 24Cxx — I2C самого Raspberry Pi (i2c-tools) — помимо Bus Pirate 5?
- Какие приборы с параметрами первыми (модель термопреобразователя/регулятора, протокол, паспорт с картой регистров)?
- Нужен ли Modbus TCP (приборы в локальной сети) — тот же навык с другим транспортом?
- Править капотом с телефона насовсем (`hood.edit: true`) или только с экрана прибора?
