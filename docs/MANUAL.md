# Часть 1. Работа с прибором

## 1.0. С чего начать: Штурман

Дирижёр сам спрашивает, чего вы хотите, и предлагает следующий шаг. Три способа открыть его — вопросы везде одинаковые:

| Что у вас | Команда | Как открыть |
|---|---|---|
| Телефон или ПК в той же сети Wi-Fi | `python3 -m dirizher web` | адрес и код доступа печатаются при запуске и видны на экране прибора («Прибор» → «Подключить телефон или ПК») |
| Сенсорный экран Pi (DSI) или монитор через переходник micro-HDMI → HDMI | служба + киоск (раздел 1.5) | экран прибора входит без кода |
| SSH, консоль через переходник USB-UART, маленький экран без графики | `python3 -m dirizher` (или `wizard`) | ответ — номер варианта, Enter — назад |

Разделы браузера: **Штурман** (цели и подсказки «сейчас важно»), **Работа** (ход сеанса и вопросы), **Журнал** (сеансы, скачать дамп), **Справочник** (переходники и движки, раздел 1.10), **Навыки** (навыки, план из STATUS.md, конструктор профиля, уроки), **Прибор** (режим, самопроверка, капот, инструменты, профили, подключение, размер текста).

Вверху в каждом разделе: **?** — справка этого раздела (поиск по статьям и урокам), **</>** — капот: код и настройки раздела (раздел 2.11).

Пример: «Починить устройство» → «Эталон уже снят» → «Сначала показать план» → Дирижёр снимет копию, проведёт диагностику и покажет, сколько секторов изменится. Ниже появится «Что дальше?» → «Выполнить по-настоящему». Запись — только после того, как вы сами введёте слово **ДА**.

Учебный режим (переключатель вверху справа) — виртуальная микросхема, железо не используется, учебные копии хранятся отдельно.

## 1.1. Как идёт сеанс `run`

| Шаг | Что происходит | Что от вас нужно |
|---|---|---|
| 1. Подготовка | Напоминание о безопасности | Проверить и нажать Enter |
| 2. Опознание | Плагины читают только идентификаторы (JEDEC ID). Подбирается профиль | Выбрать вариант, если опознание неуверенное |
| 3. Напряжение | Сверка напряжения чипа и адаптера | Подтвердить по даташиту, если в профиле напряжения нет |
| 4. Копия «до» | Чтение минимум дважды, сверка хешей; узнаётся плата по содержимому | — |
| 5. Диагностика | Проверки из профиля, сравнение с эталоном | Подтвердить эталон с другого профиля, если система спросит |
| 6. План | Способы ремонта, отсортированные по успешности; сколько секторов изменится; что сохранится с чипа | Выбрать способ |
| 7. Запись | Запись → чтение обратно → сверка → копия «после» | Ввести **ДА**; потом ответить, заработало ли устройство |

Значки находок: ✔ `ok` — норма; без значка `info` — сведения; ⚠ `warn` — замечание;
✖ `fail` — неисправность (есть способ лечения); ✖ `block` — опасно, запись запрещена.

## 1.2. Типовые сценарии

**А. Новое исправное устройство → эталон.**
`run --label "модель-плата"`. Неисправностей нет → «сохранить эталон?» → **да**.
Метка помогает различать эталоны разных устройств на одинаковых чипах.

**Б. Устройство не стартует, эталон есть.**
`run` → диагностика покажет отличия → способ «Записать эталонную прошивку» → **ДА** → проверить устройство → ответить.
Уникальные области из профиля платы (MAC, серийник) берутся с текущего чипа.

**В. Эталона нет, есть прошивка производителя.**
`run --image путь/к/файлу.bin`.
⚠ Файл обновления с сайта производителя часто **не равен** полному дампу памяти: в нём только часть разделов или свой заголовок.
Система заблокирует запись, если размер не совпадает с размером чипа. Для записи нужен полный образ всей микросхемы.

**Г. Незнакомый чип.**
`detect` → черновик в `data/drafts/`. Сверьте напряжение по даташиту, перенесите файл в `profiles/chips/`, проверьте командой `profiles`.

**Д. Не помогло.**
Ответьте «нет» (или `feedback N --fail`) → `rollback N` вернёт копию «до». Перед откатом тоже снимется копия, так что и откат можно отменить.

**Е. Ответить позже.**
На вопрос «заработало?» ответьте «позже», проверьте устройство, затем `feedback N --ok` или `--fail`.

**Ж. Забрать дамп или сравнить вручную.**
`export N --kind before --to ~/dumps/имя.bin`; два дампа можно сравнить командой `cmp -l a.bin b.bin | head`.

**З. Сначала посмотреть план.**
`run --dry-run` делает копию и диагностику, показывает план, ничего не пишет.

## 1.3. Неполадки

| Что видно | Вероятная причина | Что сделать |
|---|---|---|
| `flashrom_spi — недоступен` | flashrom не установлен | `sudo apt install flashrom` |
| Ошибка доступа к USB | нет прав | правило udev (README, раздел 2) и перелогиниться; либо разово `sudo` |
| «ничего не опознано» | прищепка, ориентация, контакт | вывод 1 по точке; переставить прищепку; `lsusb` должен показать `1a86:5512` |
| Не опознаётся только на плате | программатор питает всю плату | держать процессор в сбросе или выпаять чип |
| `not_zero`: одни нули | нет контакта или питания | см. выше; проверить 3.3 В на выводе 8 |
| `stable_read`: чтения не совпадают | плохой контакт, длинные провода, помехи | короче провода, переставить прищепку, выпаять; запись будет заблокирована, пока не станет стабильно |
| «подходят определения: …» | несколько описаний чипа с одним ID | выбрано первое; для чтения обычно не важно. Если запись не проходит сверку — приложите журнал к сессии |
| Блокировка по напряжению | чип на 1.8 В | переходник 1.8 В и `programmer_voltage: 1.8` |
| «размер образа не равен» | файл не полный дамп | нужен полный образ всего чипа (см. сценарий В) |
| «копия … повреждена» | испорчен файл в `backups/` | система сама попробует зеркало; «Самопроверка» восстановит файл (раздел 1.8); держите `mirror_dir` включённым |
| Навык или профиль «не загружен» | ошибка в правке | «Самопроверка» → «Исправить» вернёт рабочую версию из истории капота |
| Сверка после записи не совпала | контакт, питание, защита записи | система предложит вернуть копию «до»; проверьте WP (вывод 3) |

## 1.4. Без CH341A: SPI самого Raspberry Pi

У Raspberry Pi своя шина SPI с логикой 3.3 В, и проблемы с 5 В на ней нет. Подходит для выпаянного чипа или чипа в переходнике.

1. `sudo raspi-config` → Interface Options → SPI → включить, перезагрузить.
2. Подключение (SOIC-8, серия 25xx → разъём Pi):

   | Чип | Назначение | Pi (физический вывод) |
   |---|---|---|
   | 1 | CS | 24 (GPIO8, CE0) |
   | 2 | DO (MISO) | 21 (GPIO9) |
   | 3 | WP | к 3.3 В |
   | 4 | GND | 25 |
   | 5 | DI (MOSI) | 19 (GPIO10) |
   | 6 | CLK | 23 (GPIO11) |
   | 7 | HOLD | к 3.3 В |
   | 8 | VCC 3.3 В | 17 |

3. В `config.yaml`: `programmer: "linux_spi:dev=/dev/spidev0.0,spispeed=8000"`.

## 1.5. Экран прибора, телефон, ПК — подробно

- **Телефон/ПК.** `python3 -m dirizher web` → откройте `http://<адрес-прибора>:8080`, введите код. Постоянный код — `web.pin: "472913"` в `config.yaml` (в кавычках). После 5 неверных кодов вход закрывается на минуту.
- **Только экран прибора, без сети:** `web.host: 127.0.0.1`.
- **Сенсорный экран / HDMI (киоск):**
  ```
  sudo cp system/dirizher-web.service /etc/systemd/system/   # поправьте User и WorkingDirectory
  sudo systemctl daemon-reload && sudo systemctl enable --now dirizher-web
  system/kiosk.sh                                            # браузер на весь экран
  ```
  Автозапуск киоска зависит от версии Raspberry Pi OS — см. комментарии в `system/kiosk.sh` (ПРОВЕРИТЬ НА ЖЕЛЕЗЕ).
- **Без роутера:** Pi может раздать свою сеть: `sudo nmcli device wifi hotspot ssid DIRIZHER password 12345678` (ПРОВЕРИТЬ НА ЖЕЛЕЗЕ).
- **Образ прошивки с телефона:** «Починить» → «Есть файл» → «Загрузить файл с этого устройства». Файлы ложатся в `data/images/`, существующие не перезаписываются.
- Остановка службы во время записи: служба дождётся окончания операции (до 30 мин), питание не выключайте.

## 1.6. Сохранность данных

- Не удаляйте и не правьте файлы в `data/` вручную.
- Включите `mirror_dir` и раз в неделю делайте полную копию `data/` (START.md, раздел 4).
- Перед обновлением программы сделайте копию `data/`.

## 1.7. Настройка параметров прибора

Диапазон, уставка, единицы, фильтр — всё, что описано в **карте параметров** профиля (раздел 2.12).

1. «Штурман» → **Настроить прибор** → **Прочитать параметры** (только чтение). Сверьте значения с экраном прибора.
2. **Изменить параметры** → новые значения → **План без записи** или **Записать…** → слово **ДА**.
3. Дирижёр заново читает прибор (копия «до»), показывает «было → стало», пишет только изменившееся, читает обратно и сверяет. Вернуть прежние настройки — «Вернуть как было» (откат сеанса).

Командная строка: `python3 -m dirizher params`, `python3 -m dirizher tune --set range_high=600 [--dry-run]`.
Запись не начнётся, если значение вне min/max, не по шагу, параметр «только чтение» или повторные чтения не совпали.
Сквозной пример — справка «Пример: сменить диапазон термодатчика» (Modbus RTU, `skills/modbus_rtu`).

## 1.8. Самопроверка и самоисцеление

«Прибор» → **Самопроверка** или `python3 -m dirizher doctor [--heal]`.

| Что проверяется | Что чинится (по кнопке «Исправить» или `--heal`) |
|---|---|
| каждая копия дампа по SHA-256 — основное место и `mirror_dir` | испорченная или пропавшая — из исправного места; испорченный файл — в `data/quarantine/` |
| профили, навыки, лезвия, Штурман — загружаются ли | правка из капота — последней рабочей версией из истории (код и профили — со словом «ДА») |
| память SQLite, место на диске, недоступные инструменты | только сообщает |

При запуске `web` быстрая самопроверка печатается в консоли; проблемы появляются в «Сейчас важно».

## 1.9. «Что помогло»

После неудачи (не опознано, не прочиталось, сверка не совпала…) — «Записать, что помогло» в итоге сеанса или в «Журнале». Одна фраза: «переставил прищепку — вывод 1 был не там». При такой же неудаче Дирижёр покажет её первой («Раньше помогало: …»); нажмите её, если помогло снова, — подсказка поднимется выше. «Сейчас важно» само спросит, если после неудачи следующий сеанс прошёл.

## 1.10. Справочник: что подключить и кто это сделал

Вкладка **Справочник** (или `python3 -m dirizher catalog [id]` в терминале).

| Раздел | Что внутри |
|---|---|
| **Купить и подключить** | CH341A, переходник 1,8 В, прищепка SOIC-8, Bus Pirate 5, ST-Link, USBasp, USB-UART, USB–RS-485, T48, логический анализатор |
| **Собрать самому** | SPI самого Raspberry Pi, Raspberry Pi Pico как отладчик, Arduino как программатор AVR |
| **Движки** | flashrom, probe-rs, OpenOCD, minipro, AVRDUDE, esptool, binwalk, sigrok, прошивка Bus Pirate 5, Modbus RTU; основа — Python, PyYAML, SQLite |
| **Как всё связано** | для каждого вида микросхем: Дирижёр → лезвие → движок → переходники |

На карточке переходника — рисунки (провода цветом, корпус сверху с точкой у вывода 1, гребёнка с подсвеченными выводами), шаги «как подключить / собрать», «как проверить», «осторожно» и что ещё не проверено на железе. На карточке движка — авторы и лицензия, сильные стороны, как программа работает сама и что добавляет Дирижёр (копия, сверка, «ДА», журнал), пример, установка и текущее состояние лезвия.

Пополнить — **+ Карточка** (раздел 2.13). Поиск по справке (`?`) находит и карточки.

## 1.11. Приложение на телефоне (без APK)

Дирижёр устанавливается на телефон как приложение прямо из браузера (PWA): значок на главном экране,
окно без адресной строки. Отдельного APK нет и не нужно — это та же страница, что на приборе.

- **Демо:** откройте https://avtorhanov.github.io/Conductor/ в Chrome → ⋮ → «Установить приложение»
  (или «Добавить на главный экран»). После первого открытия демо запускается и без интернета.
- **Прибор по Wi-Fi** (`http://<адрес-прибора>:8080`): Chrome по адресу `http://` обычно даёт только
  «Добавить на главный экран» — ярлык, который открывает страницу во вкладке браузера (ПРОВЕРИТЬ НА ЖЕЛЕЗЕ). Полная установка
  требует HTTPS. Работать это не мешает: вход по коду и все действия те же.
- **Ничего из кэша на приборе:** сервис-воркер включается только по HTTPS (демо). Запросы `/api/…` он
  не трогает никогда — состояние прибора всегда берётся у прибора.
- Файлы: `static/manifest.webmanifest`, `static/sw.js`, значки `static/icon*.png|svg`
  (перерисовать: `python3 tools/make_icons.py`). Прибор отдаёт их без кода входа — данных прибора в них нет.

## 1.12. Учебная площадка

Пошаговый тренажёр «что и как можно сделать тем, что есть»: маршруты по устройствам и связкам. Ничего не
записывает и не трогает железо.

- **Открыть:** Штурман → «Учебная площадка» (или «Потренироваться без железа» → «Тренажёр: как думает Дирижёр»),
  адрес `/playground.html` на приборе и в демо, в терминале — `python3 -m dirizher playground [маршрут]`.
- **Маршруты:** `start` (как думает Дирижёр), `phone`, `ipad`, `meter`, `solder`, `first_chip` (Pi + CH341A —
  главная веха), `laptop` (BIOS Acer Swift 3), `car` (Лада Гранта, только чтение), `tv` (LG), `combos`, `shop`,
  `limits` (границы).
- **Шаг:** объяснение со словариком (термины нажимаются), «Зачем», «В Дирижёре», «Осторожно», «Проверить на
  железе», команды с копированием, список «сделал», вопрос «Что сделаете?» с разбором каждого ответа и «Сеанс
  вживую» — протоколы настоящего ядра на учебной микросхеме для разных ситуаций.
- **Прогресс** хранится в браузере этого устройства; тема и размер текста — как в Дирижёре.
- **Одним файлом:** `python3 -m dirizher playground --export тренажёр.html` — открывается в любом браузере без
  сети и прибора (диск, флешка, почта).

# Часть 2. Развитие

## 2.1. Архитектура

```
__main__.py (команды)
   └─ core/pipeline.py  Conductor — единый сценарий
        ├─ core/registry.py   находит плагины в plugins/
        ├─ core/profiles.py   загружает profiles/*.yaml (чип / плата / общий)
        ├─ core/checks.py     проверки диагностики (@register)
        ├─ core/safety.py     условия записи
        ├─ core/storage.py    копии по SHA-256 + зеркало
        ├─ core/memory.py     SQLite: sessions, events, snapshots, refs, recipe_stats, fixes
        ├─ core/learning.py   черновики профилей, рейтинг рецептов, «что помогло»
        ├─ core/params.py     карта параметров: кодирование полей, пределы, «было → стало»
        ├─ core/skills.py     навыки skills/<id>/ и сторож кода
        ├─ core/runner.py     запуск внешних программ: таймаут + журнал
        └─ core/ui.py         весь ввод-вывод (ConsoleUI; AutoUI для тестов)

interface/ (поверх ядра, ядро о нём не знает)
   ├─ guide.yaml    вопросы, варианты, уроки — правятся без программирования
   ├─ guide.py      Штурман: подсказки по журналу, «что дальше», выполнение действий
   ├─ web.py        браузер: HTTP на стандартной библиотеке, WebUI, вход по коду
   ├─ static/index.html  одна страница для телефона, ПК и экрана прибора
   ├─ wizard.py     тот же Штурман в терминале
   ├─ builder.py    конструктор профиля чипа
   ├─ playground.yaml + playground.py  учебная площадка: маршруты, проверка, текстовый режим
   └─ static/playground.html  страница тренажёра (прибор, демо, отдельный файл)

workshop/ (мастерская, поверх ядра)
   ├─ hood.py        капот: что можно править, проверка, история версий, возврат
   ├─ skillmaker.py  навыки и статьи справки из шаблонов
   ├─ helpdocs.py    справка: help/*.md + справка навыков + уроки + карточки, поиск
   ├─ catalog.py     справочник: карточки движков и переходников, проверка, рисунки данными, конструктор
   └─ doctor.py      самопроверка и самоисцеление

catalog/      справочник: engines/*.yaml, adapters/*.yaml, шаблоны _template_*.yaml
tools/build_pages.py + pages_demo.js   демо для GitHub Pages (раздел 2.14)

skills/<id>/  навыки: skill.yaml, skill.py, profiles/, help.md   (пример — modbus_rtu)
help/*.md     статьи справки
```

Правило слоёв: «как подключиться» — плагин, «что это и как лечить» — профиль, «в каком порядке и с какой защитой» — ядро.

## 2.2. Профиль чипа или платы

Шаблоны с комментариями к каждому полю: `profiles/chips/_template.yaml` и `profiles/boards/_template_board.yaml`.

- `match` — поля отпечатка, которые даёт плагин (`jedec_id`, `name`…). Значение может быть списком.
- `content_match` — сигнатуры в дампе. Профиль с ними считается профилем платы и проверяется после чтения.
- `preserve` — уникальные области платы (`offset`, `length`, `why`).
- `checks` — проверки по порядку (имена из `core/checks.py`). `recipes` — способы ремонта (`action`: `write_reference` или `write_image`).
- `params` и `bus` — карта параметров для «Настройки» (раздел 2.12).
- Профиль с пустым `match` — общий профиль класса (низкая уверенность).

Проверка: `python3 -m dirizher profiles` — ошибки в профилях будут показаны.

## 2.3. Новая проверка

В `core/checks.py`:
```python
import zlib   # в начало файла

@register("crc32_region")
def crc32_region(ci: CheckInput) -> Finding:
    off, ln = to_int(ci.params["offset"]), to_int(ci.params["length"])
    want = to_int(ci.params["crc"])
    got = zlib.crc32(ci.data[off:off + ln])
    if got == want:
        return Finding("crc32_region", "ok", "контрольная сумма раздела верна")
    return Finding("crc32_region", "fail", f"CRC раздела 0x{got:08X}, ожидалось 0x{want:08X}",
                   ["restore_reference", "restore_image"])
```
Затем добавьте в профиль: `- type: crc32_region` с параметрами.
Проверки **только читают** `ci.data`. Статус `block` используйте лишь там, где запись опасна.

## 2.4. Новый плагин (лезвие)

1. `cp dirizher/plugins/_template.py dirizher/plugins/<имя>.py` (без `_` в начале).
2. Задайте `name`, `title`, `target_class` и реализуйте `available / probe / read / write`.
3. Включите в `config.yaml` → `plugins: <имя>: enabled: true` (+ свои настройки, они придут в `self.settings`).
4. Создайте профили с `class: <target_class>`.
5. Тесты (2.6).

Правила:
- `probe()` — только чтение идентификаторов;
- внешние программы — через `self.run(cmd, timeout)`;
- ошибки — `raise RuntimeError("понятный текст")`;
- копии, сверку и подтверждение делает ядро, в плагине их не дублировать;
- если формат вывода программы не проверен на железе, пометьте это в коде и в `docs/STATUS.md`.

**Тестирование без железа — подставная программа.** Создайте скрипт с именем настоящей программы
(например, `flashrom`), который печатает типичный вывод и читает/пишет файл вместо чипа. Положите его
в папку и поставьте её первой в `PATH`. Так проверяется разбор вывода и весь цикл; на железе
остаётся проверить только реальный формат.

## 2.5. Новое действие рецепта

Сейчас их два: `write_reference` и `write_image`. Новое действие (например, запись одного раздела)
меняет ядро: `KNOWN_ACTIONS` в `core/profiles.py` и `build_image()` в `core/pipeline.py`.
Делайте это только с тестами на все случаи и только через `Conductor.apply()`: он гарантирует копию, сверку и копию «после».

## 2.6. Тесты

- Запуск: `python3 -m unittest -v`. Они должны проходить **до каждого коммита**.
- Сценарии ядра — `tests/test_pipeline.py` (симулятор + `AutoUI`).
- Для нового плагина — свой файл `tests/test_<плагин>.py` с подставной программой.
- Любая ошибка, найденная на железе, сначала воспроизводится тестом, потом исправляется.

## 2.7. Штурман: свой вопрос, вариант или урок

Всё в `dirizher/interface/guide.yaml`. Вариант ведёт ровно в одно место: `next` (вопрос), `action` (действие) или `lesson` (урок).
```yaml
- label: Роутер не грузится после обновления
  explain: частый случай — оборванная запись
  next: repair
- label: Сначала план без записи
  action: run
  params: {dry_run: true, label: ask}    # ask — спросить метку у человека
```
Урок — `title`, `why`, `steps` (строка или `text` + `code`), `check`, `related`, `group: work | dev`.
Действия: `run`, `detect`, `rollback`, `feedback`, `reference`, `export`, `sim` (`do`), `history`, `plugins`, `profiles`, `roadmap`, `builder`, `capture` (`scan: true` — найти анализатор; замер только принимает сигналы); с 0.4.0 — `params`, `tune` (`set`), `tune_form`, `skills`, `help` (`article`), `hood` (`area`), `doctor`, `fix`.
Проверка: `python3 -m unittest tests.test_interface -v` — тест ловит опечатки в ссылках и недостижимые вопросы. Затем обновите страницу.

Подсказки «сейчас важно» и «что дальше» — функции `suggest()` и `after()` в `guide.py`. Новое правило подсказки — новая строка там же + тест.

## 2.8. Новый экран или способ управления

Ядро общается с человеком только через объект `ui` (методы `info/ok/warn/error/finding/step/header` и вопросы `pause/yes_no/choose/confirm_word`). Новый интерфейс = свой класс `ui` + вызовы `guide.execute()`. Пример — `WebUI` в `web.py`: вопросы ядра становятся карточками, ответы возвращаются в ядро.
Правила: «Отмена» = безопасный ответ (как пустой ввод в консоли); слово подтверждения проверяет сервер, а не кнопка; запись — только через `Conductor.apply()`.

## 2.9. Соглашения

- Python 3.9+, из внешних библиотек в ядре только PyYAML.
- Тексты для человека — по-русски и понятно неспециалисту; идентификаторы в коде — по-английски.
- Ядро не знает о конкретных чипах. Данные никогда не удаляются. Запись идёт только через `Conductor.apply()`.
- Версии: `0.MINOR.PATCH`. Новое лезвие повышает MINOR. Каждое изменение записывается в `CHANGELOG.md`.

## 2.10. Навыки

Навык — папка `skills/<id>/`, которая добавляет умение без правки пакета. Быстрее всего — «Навыки» → **+ Навык** (нужен открытый капот): Дирижёр создаст файлы из шаблона и откроет главный в капоте.

| Вид | Когда | Файлы |
|---|---|---|
| Карта параметров | прибор уже виден лезвию (например, Modbus RTU) — описать его настройки | `skill.yaml`, `profiles/<id>.yaml`, `help.md` |
| Инструмент (протокол) | свой протокол или программа | `skill.yaml`, `skill.py` (лезвие), `help.md` |
| Проверка | новая диагностика дампа | `skill.yaml`, `skill.py` (`@register`), `help.md` |

- `skill.yaml`: `id` (= имя папки), `title`, `kind`, `enabled` (загружать ли навык), `settings` — настройки лезвия по умолчанию (`config.yaml` → `plugins: <имя>` важнее). Лезвие нового навыка выключено: `settings: enabled: false`.
- Код навыка импортирует ядро абсолютно: `from dirizher.core.plugin import Plugin`. Порт или программа — отдельным процессом через `self.run([sys.executable, str(HELPER), …])`, как `skills/modbus_rtu/rtu.py`.
- Сторож (`core/skills.lint`) не загрузит код с удалением файлов, `subprocess`/`os.system`, `eval`/`exec`, доступом к `self.c.store` и записью из `probe()`. Сеть — предупреждение.
- Изменённый `skill.py` подхватывается при следующем действии (по времени изменения файла). Сломанный навык не роняет систему: причина видна в «Навыках», `skills` и самопроверке.
- Тест — как для плагина (2.6): эмулятор или подставная программа. Пример — `tests/fakes/modbus_emulator.py` и `tests/test_params.py`.

## 2.11. Капот

Кнопка **</>** открывает файлы раздела; полный порядок — `dirizher/workshop/hood.py`.

- **Править можно:** `skills/**`, `profiles/**`, `help/*.md`, `catalog/**` (карточки справочника — без слова «ДА»: они только описывают), `dirizher/interface/guide.yaml`, `dirizher/plugins/*.py`.
- **Только смотреть:** `dirizher/core/**` (порядок работы и защита), `config.yaml`, `plugins/_common.py` (сторож лезвий), `plugins/simulator.py` (эталон тестов), интерфейсы и помощники. Их меняют через git с тестами.
- **Сохранение:** проверка (YAML; профиль — как его загрузит ядро, без повторов id; паспорт навыка; Штурман; код — синтаксис, сторож, пробный импорт отдельным процессом) → прежняя версия в `data/hood/history/` → атомарная запись. Код и профили — со словом **ДА**.
- **История:** любую версию можно вернуть — это тоже правка с историей. Журнал правок — `data/hood/journal.jsonl` (кто: экран прибора или адрес в сети).
- **Открыть:** «Прибор» → «Открыть капот» на экране самого прибора (до перезапуска) или `hood.edit: true` в `config.yaml`. С телефона открыть нельзя: правка кода = выполнение кода на приборе.

Правка в капоте — для быстрых исправлений на месте. Всё, что прижилось, переносите в git и покрывайте тестом (2.6).

## 2.12. Карта параметров

Поля профиля (подробно — справка «Параметры прибора», `core/params.py`):

```yaml
bus: {start: 0, count: 8, function: 3}   # окно для лезвия (у Modbus — регистры настроек)
params:
  - id: range_high              # латиница
    title: Верхняя граница
    register: 3                 # или offset: 0x22 (байт)
    type: i16be                 # u8 i8 u16be u16le i16be i16le u32be u32le i32be i32le f32be f32le
    scale: 0.1
    unit: "°C"
    min: -200
    max: 1300
    writable: true
    choices: {0: Pt100, 1: Pt1000}
    help: Что это и где в паспорте
```

- Параметры не пересекаются и не выходят за `size` — иначе профиль не загрузится (и капот не сохранит).
- В окно Modbus не включайте измеряемые величины: повторные чтения не совпадут, запись заблокируется.
- Адрес и скорость прибора делайте `writable: false`: после их смены сверка по старому адресу невозможна. Для эталона настроек добавьте их в `preserve`.
- Новая карта — «ПРОВЕРИТЬ НА ЖЕЛЕЗЕ»: сначала «Прочитать параметры» и сверить с экраном прибора.

## 2.13. Карточки справочника

Файл `catalog/engines/<id>.yaml` или `catalog/adapters/<id>.yaml` (навык — `skills/<навык>/catalog/*.yaml`). Поля с комментариями — в шаблонах `catalog/_template_engine.yaml` и `catalog/_template_adapter.yaml`; проверка — `workshop/catalog.validate()`.

- Обязательно: `id` (= имя файла), `kind` (`engine` | `adapter`), `title`, `tagline`. У движка — `authors` и `license` (иначе самопроверка напомнит).
- Связи: у движка `adapters`, `plugin` (статус лезвия), `program` (установлена ли), `lesson` (урок Штурмана); у переходника `engines`, `needs`. Ссылки на несуществующие карточки — предупреждение, не ошибка.
- Рисунки — данными, их рисует интерфейс (SVG без картинок и сети) и терминал (строками):

```yaml
drawings:
  - type: wiring                      # провода: a — слева, b — справа
    a_title: Raspberry Pi
    b_title: Флешка 25xx
    wires: [{a: "24 · CE0", b: "1 · CS", color: orange, note: "первым"}]
  - type: package                     # корпус сверху, подписи с 1-го вывода
    style: soic                       # или dip
    pins: [CS, DO, WP, GND, DI, CLK, HOLD, VCC]
    mark: {CS: orange}
  - type: header                      # гребёнка: нечётные выводы — верхний ряд
    count: 40
    rows: 2
    pins: {17: {label: "3,3 В", color: red, to: "VCC (8)"}}
  - type: chain                       # что к чему
    steps: [Raspberry Pi, CH341A, Прищепка, Микросхема]
```

Цвета: red black orange yellow green blue violet white gray brown. Строку с «: » внутри — в кавычки.
Конструктор («Справочник» → «+ Карточка») собирает YAML из формы, рисует схему сразу и сохраняет через капот (история, ничего не перезаписывается). Тесты — `tests/test_catalog.py`.

## 2.14. Демо на GitHub Pages

`python3 tools/build_pages.py` собирает `_site/`: ту же страницу `static/index.html` + `tools/pages_demo.js` (подмена связи: запросы `/api/…` отвечаются из `demo/*.json`).

- Данные записывает **настоящее ядро**: сборщик запускает веб-сервер в учебном режиме на копии проекта и проходит задания на виртуальной микросхеме во всех её состояниях (исправна / повреждена / стёрта, плохой контакт, есть ли эталон) и со всеми ответами (`ДА` и неверное слово, да / нет / позже, выбор). В демо ответ выбирает ветку — как на приборе.
- Сохранение, капот, «что помогло», загрузка образа и скачивание дампа в демо не работают — страница говорит об этом.
- Публикация — `.github/workflows/pages.yml` при каждом push в `main`: тесты → сборка → Pages. Один раз включите **Settings → Pages → Source: GitHub Actions**.
- Файлы приложения (манифест, значки, `sw.js`) кладутся в `_site/` из `web.APP_FILES` — демо устанавливается на телефон.
- Изменили интерфейс или Штурман — демо обновится само при следующей публикации. Проверить локально: `python3 -m http.server -d _site 8000`.

## 2.15. Учебная площадка: свой маршрут или шаг

Содержание — данные: `dirizher/interface/playground.yaml` (поля описаны в начале файла), страница —
`static/playground.html`, загрузка, проверка и текстовый режим — `interface/playground.py`. Ядро не меняется.

- Правка — в капоте (раздел «Штурман», без слова «ДА»: это учебный текст) или через git.
- Проверка при сохранении и в тестах (`tests/test_playground.py`): обязательные поля, у вопроса есть верный ответ,
  термины `[[…]]` есть в словарике, `next` ведёт на существующие маршруты, ссылки — только `https://`.
- **Сеанс вживую:** строки — как печатает ядро. С `check: <сценарий>` тест запускает настоящее ядро на учебной
  микросхеме и сверяет каждую строку (числа и отпечатки не сравниваются). Строка с `~` — пример (например,
  вывод настоящего flashrom), `? ! >` — диалог, ` …` в конце — строка сокращена.
- Прибор отдаёт `/playground.html` и `/playground.json` без кода входа (`web.PLAYGROUND_FILES`): там только учебный
  текст. Демо (`tools/build_pages.py`) кладёт те же два файла в `_site/`.
