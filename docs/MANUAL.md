# Часть 1. Работа с прибором

## 1.0. С чего начать: Штурман

Дирижёр сам спрашивает, чего вы хотите, и предлагает следующий шаг. Три способа открыть его — вопросы везде одинаковые:

| Что у вас | Команда | Как открыть |
|---|---|---|
| Телефон или ПК в той же сети Wi-Fi | `python3 -m dirizher web` | адрес и код доступа печатаются при запуске и видны на экране прибора («Прибор» → «Подключить телефон или ПК») |
| Сенсорный экран Pi (DSI) или монитор через переходник micro-HDMI → HDMI | служба + киоск (раздел 1.5) | экран прибора входит без кода |
| SSH, консоль через переходник USB-UART, маленький экран без графики | `python3 -m dirizher` (или `wizard`) | ответ — номер варианта, Enter — назад |

Разделы браузера: **Штурман** (цели и подсказки «сейчас важно»), **Работа** (ход сеанса и вопросы), **Журнал** (сеансы, скачать дамп), **Развитие** (план из STATUS.md, конструктор профиля, уроки), **Прибор** (режим, инструменты, профили, подключение, размер текста).

Пример: «Починить устройство» → «Эталон уже снят» → «Сначала показать план» → Дирижёр снимет копию, проведёт диагностику и покажет, сколько секторов изменится. Ниже появится «Что дальше?» → «Выполнить по-настоящему». Запись — только после того, как вы сами введёте слово **ДА**.

Учебный режим (переключатель вверху справа) — виртуальная микросхема, железо не используется, учебные копии хранятся отдельно.

## 1.1. Как идёт сеанс `run`

| Шаг | Что происходит | Что от вас нужно |
|---|---|---|
| 1. Подготовка | Напоминание о безопасности | Проверить и нажать Enter |
| 2. Опознание | Плагины читают только идентификаторы (JEDEC ID). Подбирается профиль | Выбрать вариант, если опознание неуверенное |
| 3. Напряжение | Сверка напряжения чипа и адаптера | Подтвердить по даташиту, если в профиле напряжения нет |
| 4. Копия «до» | Чтение минимум дважды, сверка хешей; узнаётся плата по содержимому | — |
| 5. Диагностика | Проверки из профиля, сравнение с эталоном | Подтвердить эталон с другого профиля, если система спросит |
| 6. План | Способы ремонта, отсортированные по успешности; сколько секторов изменится; что сохранится с чипа | Выбрать способ |
| 7. Запись | Запись → чтение обратно → сверка → копия «после» | Ввести **ДА**; потом ответить, заработало ли устройство |

Значки находок: ✔ `ok` — норма; без значка `info` — сведения; ⚠ `warn` — замечание;
✖ `fail` — неисправность (есть способ лечения); ✖ `block` — опасно, запись запрещена.

## 1.2. Типовые сценарии

**А. Новое исправное устройство → эталон.**
`run --label "модель-плата"`. Неисправностей нет → «сохранить эталон?» → **да**.
Метка помогает различать эталоны разных устройств на одинаковых чипах.

**Б. Устройство не стартует, эталон есть.**
`run` → диагностика покажет отличия → способ «Записать эталонную прошивку» → **ДА** → проверить устройство → ответить.
Уникальные области из профиля платы (MAC, серийник) берутся с текущего чипа.

**В. Эталона нет, есть прошивка производителя.**
`run --image путь/к/файлу.bin`.
⚠ Файл обновления с сайта производителя часто **не равен** полному дампу памяти: в нём только часть разделов или свой заголовок.
Система заблокирует запись, если размер не совпадает с размером чипа. Для записи нужен полный образ всей микросхемы.

**Г. Незнакомый чип.**
`detect` → черновик в `data/drafts/`. Сверьте напряжение по даташиту, перенесите файл в `profiles/chips/`, проверьте командой `profiles`.

**Д. Не помогло.**
Ответьте «нет» (или `feedback N --fail`) → `rollback N` вернёт копию «до». Перед откатом тоже снимется копия, так что и откат можно отменить.

**Е. Ответить позже.**
На вопрос «заработало?» ответьте «позже», проверьте устройство, затем `feedback N --ok` или `--fail`.

**Ж. Забрать дамп или сравнить вручную.**
`export N --kind before --to ~/dumps/имя.bin`; два дампа можно сравнить командой `cmp -l a.bin b.bin | head`.

**З. Сначала посмотреть план.**
`run --dry-run` делает копию и диагностику, показывает план, ничего не пишет.

## 1.3. Неполадки

| Что видно | Вероятная причина | Что сделать |
|---|---|---|
| `flashrom_spi — недоступен` | flashrom не установлен | `sudo apt install flashrom` |
| Ошибка доступа к USB | нет прав | правило udev (README, раздел 2) и перелогиниться; либо разово `sudo` |
| «ничего не опознано» | прищепка, ориентация, контакт | вывод 1 по точке; переставить прищепку; `lsusb` должен показать `1a86:5512` |
| Не опознаётся только на плате | программатор питает всю плату | держать процессор в сбросе или выпаять чип |
| `not_zero`: одни нули | нет контакта или питания | см. выше; проверить 3.3 В на выводе 8 |
| `stable_read`: чтения не совпадают | плохой контакт, длинные провода, помехи | короче провода, переставить прищепку, выпаять; запись будет заблокирована, пока не станет стабильно |
| «подходят определения: …» | несколько описаний чипа с одним ID | выбрано первое; для чтения обычно не важно. Если запись не проходит сверку — приложите журнал к сессии |
| Блокировка по напряжению | чип на 1.8 В | переходник 1.8 В и `programmer_voltage: 1.8` |
| «размер образа не равен» | файл не полный дамп | нужен полный образ всего чипа (см. сценарий В) |
| «копия … повреждена» | испорчен файл в `backups/` | система сама попробует зеркало; держите `mirror_dir` включённым |
| Сверка после записи не совпала | контакт, питание, защита записи | система предложит вернуть копию «до»; проверьте WP (вывод 3) |

## 1.4. Без CH341A: SPI самого Raspberry Pi

У Raspberry Pi своя шина SPI с логикой 3.3 В, и проблемы с 5 В на ней нет. Подходит для выпаянного чипа или чипа в переходнике.

1. `sudo raspi-config` → Interface Options → SPI → включить, перезагрузить.
2. Подключение (SOIC-8, серия 25xx → разъём Pi):

   | Чип | Назначение | Pi (физический вывод) |
   |---|---|---|
   | 1 | CS | 24 (GPIO8, CE0) |
   | 2 | DO (MISO) | 21 (GPIO9) |
   | 3 | WP | к 3.3 В |
   | 4 | GND | 25 |
   | 5 | DI (MOSI) | 19 (GPIO10) |
   | 6 | CLK | 23 (GPIO11) |
   | 7 | HOLD | к 3.3 В |
   | 8 | VCC 3.3 В | 17 |

3. В `config.yaml`: `programmer: "linux_spi:dev=/dev/spidev0.0,spispeed=8000"`.

## 1.5. Экран прибора, телефон, ПК — подробно

- **Телефон/ПК.** `python3 -m dirizher web` → откройте `http://<адрес-прибора>:8080`, введите код. Постоянный код — `web.pin: "472913"` в `config.yaml` (в кавычках). После 5 неверных кодов вход закрывается на минуту.
- **Только экран прибора, без сети:** `web.host: 127.0.0.1`.
- **Сенсорный экран / HDMI (киоск):**
  ```
  sudo cp system/dirizher-web.service /etc/systemd/system/   # поправьте User и WorkingDirectory
  sudo systemctl daemon-reload && sudo systemctl enable --now dirizher-web
  system/kiosk.sh                                            # браузер на весь экран
  ```
  Автозапуск киоска зависит от версии Raspberry Pi OS — см. комментарии в `system/kiosk.sh` (ПРОВЕРИТЬ НА ЖЕЛЕЗЕ).
- **Без роутера:** Pi может раздать свою сеть: `sudo nmcli device wifi hotspot ssid DIRIZHER password 12345678` (ПРОВЕРИТЬ НА ЖЕЛЕЗЕ).
- **Образ прошивки с телефона:** «Починить» → «Есть файл» → «Загрузить файл с этого устройства». Файлы ложатся в `data/images/`, существующие не перезаписываются.
- Остановка службы во время записи: служба дождётся окончания операции (до 30 мин), питание не выключайте.

## 1.6. Сохранность данных

- Не удаляйте и не правьте файлы в `data/` вручную.
- Включите `mirror_dir` и раз в неделю делайте полную копию `data/` (START.md, раздел 4).
- Перед обновлением программы сделайте копию `data/`.

# Часть 2. Развитие

## 2.1. Архитектура

```
__main__.py (команды)
   └─ core/pipeline.py  Conductor — единый сценарий
        ├─ core/registry.py   находит плагины в plugins/
        ├─ core/profiles.py   загружает profiles/*.yaml (чип / плата / общий)
        ├─ core/checks.py     проверки диагностики (@register)
        ├─ core/safety.py     условия записи
        ├─ core/storage.py    копии по SHA-256 + зеркало
        ├─ core/memory.py     SQLite: sessions, events, snapshots, refs, recipe_stats
        ├─ core/learning.py   черновики профилей, рейтинг рецептов
        ├─ core/runner.py     запуск внешних программ: таймаут + журнал
        └─ core/ui.py         весь ввод-вывод (ConsoleUI; AutoUI для тестов)

interface/ (поверх ядра, ядро о нём не знает)
   ├─ guide.yaml    вопросы, варианты, уроки — правятся без программирования
   ├─ guide.py      Штурман: подсказки по журналу, «что дальше», выполнение действий
   ├─ web.py        браузер: HTTP на стандартной библиотеке, WebUI, вход по коду
   ├─ static/index.html  одна страница для телефона, ПК и экрана прибора
   ├─ wizard.py     тот же Штурман в терминале
   └─ builder.py    конструктор профиля чипа
```

Правило слоёв: «как подключиться» — плагин, «что это и как лечить» — профиль, «в каком порядке и с какой защитой» — ядро.

## 2.2. Профиль чипа или платы

Шаблоны с комментариями к каждому полю: `profiles/chips/_template.yaml` и `profiles/boards/_template_board.yaml`.

- `match` — поля отпечатка, которые даёт плагин (`jedec_id`, `name`…). Значение может быть списком.
- `content_match` — сигнатуры в дампе. Профиль с ними считается профилем платы и проверяется после чтения.
- `preserve` — уникальные области платы (`offset`, `length`, `why`).
- `checks` — проверки по порядку (имена из `core/checks.py`). `recipes` — способы ремонта (`action`: `write_reference` или `write_image`).
- Профиль с пустым `match` — общий профиль класса (низкая уверенность).

Проверка: `python3 -m dirizher profiles` — ошибки в профилях будут показаны.

## 2.3. Новая проверка

В `core/checks.py`:
```python
import zlib   # в начало файла

@register("crc32_region")
def crc32_region(ci: CheckInput) -> Finding:
    off, ln = to_int(ci.params["offset"]), to_int(ci.params["length"])
    want = to_int(ci.params["crc"])
    got = zlib.crc32(ci.data[off:off + ln])
    if got == want:
        return Finding("crc32_region", "ok", "контрольная сумма раздела верна")
    return Finding("crc32_region", "fail", f"CRC раздела 0x{got:08X}, ожидалось 0x{want:08X}",
                   ["restore_reference", "restore_image"])
```
Затем добавьте в профиль: `- type: crc32_region` с параметрами.
Проверки **только читают** `ci.data`. Статус `block` используйте лишь там, где запись опасна.

## 2.4. Новый плагин (лезвие)

1. `cp dirizher/plugins/_template.py dirizher/plugins/<имя>.py` (без `_` в начале).
2. Задайте `name`, `title`, `target_class` и реализуйте `available / probe / read / write`.
3. Включите в `config.yaml` → `plugins: <имя>: enabled: true` (+ свои настройки, они придут в `self.settings`).
4. Создайте профили с `class: <target_class>`.
5. Тесты (2.6).

Правила:
- `probe()` — только чтение идентификаторов;
- внешние программы — через `self.run(cmd, timeout)`;
- ошибки — `raise RuntimeError("понятный текст")`;
- копии, сверку и подтверждение делает ядро, в плагине их не дублировать;
- если формат вывода программы не проверен на железе, пометьте это в коде и в `docs/STATUS.md`.

**Тестирование без железа — подставная программа.** Создайте скрипт с именем настоящей программы
(например, `flashrom`), который печатает типичный вывод и читает/пишет файл вместо чипа. Положите его
в папку и поставьте её первой в `PATH`. Так проверяется разбор вывода и весь цикл; на железе
остаётся проверить только реальный формат.

## 2.5. Новое действие рецепта

Сейчас их два: `write_reference` и `write_image`. Новое действие (например, запись одного раздела)
меняет ядро: `KNOWN_ACTIONS` в `core/profiles.py` и `build_image()` в `core/pipeline.py`.
Делайте это только с тестами на все случаи и только через `Conductor.apply()`: он гарантирует копию, сверку и копию «после».

## 2.6. Тесты

- Запуск: `python3 -m unittest -v`. Они должны проходить **до каждого коммита**.
- Сценарии ядра — `tests/test_pipeline.py` (симулятор + `AutoUI`).
- Для нового плагина — свой файл `tests/test_<плагин>.py` с подставной программой.
- Любая ошибка, найденная на железе, сначала воспроизводится тестом, потом исправляется.

## 2.7. Штурман: свой вопрос, вариант или урок

Всё в `dirizher/interface/guide.yaml`. Вариант ведёт ровно в одно место: `next` (вопрос), `action` (действие) или `lesson` (урок).
```yaml
- label: Роутер не грузится после обновления
  explain: частый случай — оборванная запись
  next: repair
- label: Сначала план без записи
  action: run
  params: {dry_run: true, label: ask}    # ask — спросить метку у человека
```
Урок — `title`, `why`, `steps` (строка или `text` + `code`), `check`, `related`, `group: work | dev`.
Действия: `run`, `detect`, `rollback`, `feedback`, `reference`, `export`, `sim` (`do`), `history`, `plugins`, `profiles`, `roadmap`, `builder`.
Проверка: `python3 -m unittest tests.test_interface -v` — тест ловит опечатки в ссылках и недостижимые вопросы. Затем обновите страницу.

Подсказки «сейчас важно» и «что дальше» — функции `suggest()` и `after()` в `guide.py`. Новое правило подсказки — новая строка там же + тест.

## 2.8. Новый экран или способ управления

Ядро общается с человеком только через объект `ui` (методы `info/ok/warn/error/finding/step/header` и вопросы `pause/yes_no/choose/confirm_word`). Новый интерфейс = свой класс `ui` + вызовы `guide.execute()`. Пример — `WebUI` в `web.py`: вопросы ядра становятся карточками, ответы возвращаются в ядро.
Правила: «Отмена» = безопасный ответ (как пустой ввод в консоли); слово подтверждения проверяет сервер, а не кнопка; запись — только через `Conductor.apply()`.

## 2.9. Соглашения

- Python 3.9+, из внешних библиотек в ядре только PyYAML.
- Тексты для человека — по-русски и понятно неспециалисту; идентификаторы в коде — по-английски.
- Ядро не знает о конкретных чипах. Данные никогда не удаляются. Запись идёт только через `Conductor.apply()`.
- Версии: `0.MINOR.PATCH`. Новое лезвие повышает MINOR. Каждое изменение записывается в `CHANGELOG.md`.
