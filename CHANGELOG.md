## 0.7.0 — в работе «Порядок и универсальность»
План — `docs/PLAN.md`; каждая сессия дописывает свой подраздел.

### S1. Журнал → тест, версия программы (2026-11-25)
- **Полный вывод команд.** `Runner` сохраняет stdout/stderr каждой команды целиком (до 1 МБ на поток) отдельным
  файлом `data/logs/session_NNNNN/cmd_NNN.json` (команда, код, время, вывод); в событии — прежний хвост и ссылка
  `file:`. Файлы только добавляются. Дампы туда не попадают: чтение идёт во временные файлы, а `probe-rs read`
  (дамп в stdout) вызывается с `keep_output=False` — вывод не сохраняется ни в файл, ни в хвост события.
- **`Plugin.version()`** → строка или `None`. Реализовано: flashrom (`--version`), probe-rs (`--version`),
  OpenOCD (`--version`), minipro (`--version`), avrdude (`-?`), esptool (`version`, та же команда, что для v4/v5),
  симулятор. Ядро зовёт её один раз за сеанс после опознания: событие «инструмент: … , версия …» с настройками
  лезвия. В отпечаток не входит. Общий помощник `_common.tool_version()`.
- **Пакет журнала для разработки** (`core/journal.py`): команды, коды возврата, полный вывод, версии, настройки
  лезвия, отпечаток, снимки (только хеши), события, итог — без дампов. Очистка: MAC → `02:00:00:00:00:NN`
  (один MAC — одна заглушка), серийные номера / «Serial code» / серийник в `VID:PID:…` и `/dev/serial/by-id/…`
  → `SERIAL-N`, имя хоста → `host`, домашние пути → `~`.
  CLI: `python3 -m dirizher journal N [--to файл.json]` (чужой файл не переписывается).
  Веб: «Журнал» → сеанс → «Скачать журнал для разработки» (`/api/journal`), с телефона скачивается файл.
- **`tools/log_to_test.py пакет.json`** → `tests/fixtures/real/<программа>_<версия>_<n>.json` (команды, настройки,
  ожидаемое опознание из сеанса; `--expect ключ=значение` поправить) и сразу прогон через плагин.
  `tests/test_real_outputs.py` прогоняет каждую фикстуру через настоящий плагин с подменным Runner
  (`ReplayRunner`: ответ по команде, временные пути не важны). Пока с железа ничего нет — одна синтетическая
  фикстура `flashrom_synthetic_1.json` (`"synthetic": true`).
- Подставной `flashrom` в `tests/fakes/fake_tools.py` (длинный `-V`: строка RDID далеко от хвоста), команды версии
  у подставных probe-rs, OpenOCD, minipro, avrdude.
- Справка `help/journal.md` «Журнал для разработки: как передать прогон с железа».
- Версия пакета — 0.7.0.
- 17 автотестов (всего 230). В трёх прежних тестах «опознание только читает» (probe-rs, minipro, avrdude) к
  разрешённым командам добавлена команда версии — она тоже только читает; смысл тестов прежний.
- Ядро: `runner.py` (сохранение вывода, `keep_output`), `plugin.py` (`version()`, `keep_output`), `pipeline.py`
  (файл вывода, событие версии в `_record_detection`), новый `journal.py`. Ответы ядра и сценарии прежние.

### S2a. Схема настроек лезвий, форма в «Прибор» (2026-11-25)
- **`Plugin.settings_schema`** (новый `core/settings.py`): поле — `key`, `title`, `type` (str, int, float, bool,
  choice, list, port, path), `required`, `default`, `example`, `help`, `choices`, `safety: voltage`, `hex`.
  Общие поля (`enabled`, `programmer_voltage`, `extra_args`, таймауты) описаны один раз; лезвие выбирает нужные
  (`common_settings`) и свои умолчания (`settings_defaults`). `Plugin.schema()`, `Plugin.has_schema()`.
  Схемы заполнены у flashrom_spi, probe_rs, openocd, minipro, avrdude, esptool, bp5_i2c, симулятора и навыка
  modbus_rtu; у шаблона лезвия и шаблона навыка-инструмента — образец.
- **Проверка по схеме при загрузке** (`registry.load_plugins`): неизвестный ключ — предупреждение с догадкой
  («flash_sise — может быть, flash_size?») в отчёте плагинов (`warnings`), `plugins`, самопроверке и форме;
  у включённого лезвия нет обязательного поля — «недоступен: укажите «…» (ключ)»; неверный тип — «нужно целое
  число, а указано «…»». Лезвия без схемы (старые, свои) — неизвестные ключи не проверяются. `available()` прежний.
- **`config.tools.yaml`** рядом с `config.yaml` (в `.gitignore`): только секция `plugins:`, читается после
  `config.yaml` и перекрывает его ключ за ключом (null не перекрывает). Сломанный файл не действует, самопроверка
  показывает его и возвращает рабочую версию из истории капота. `config.yaml` программа по-прежнему не правит.
  Сохранение — через капот: проверка по схемам, история версий, слово «ДА», только при открытом капоте.
- **Форма в вебе:** «Прибор» → «Инструменты» → «Настроить» (`/api/tool`, `/api/tool/check`, `/api/tool/save`):
  поля по схеме, текущее значение и откуда оно (config.tools.yaml / config.yaml / навык / по умолчанию), подсказка,
  пример; поля напряжения выделены с предупреждением; «Проверить» (без записи, со статусом лезвия «как станет»)
  и «Сохранить…» (слово «ДА»), после — статус заново. Пустое поле — убрать ключ из config.tools.yaml.
- **Мастер в терминале:** «Прибор» → выбрать инструмент → поле за полем (Enter — оставить, «-» — убрать).
  **CLI:** `python3 -m dirizher tool [имя] [--set ключ=значение …] [--check]` — слово спрашивается всегда.
  Действие Штурмана `tool` (`params: {name}`); в уроках по инструментам — «Настроить … (форма)».
- **Самопроверка:** опечатки и неверные типы в настройках лезвий; `probe_rs` и `openocd` включены вместе — предупреждение.
- Тест: ключи `docs/config-snippet-0.3.0.yaml` (и закомментированные образцы) есть в схемах.
- 15 автотестов (`tests/test_settings.py`), в т. ч. включение лезвия с экрана по HTTP без правки `config.yaml`
  и «напряжение без слова не меняется». Прежние тесты не менялись.
- Ядро: новый `core/settings.py`; `plugin.py` (схема), `registry.py` (проверка), `config.py` (config.tools.yaml).
  Ответы ядра и сценарии прежние; новый текст статуса — только для включённого лезвия без обязательного поля.

### S2b. Модель цели из профиля, «начать с переходника» (2026-11-25)
- **Поле профиля `tool:`** — настройки лезвий для этой модели, размер берётся из `size`
  (`Plugin.size_setting`). Заполнено у `stm32f103c8` (probe_rs, openocd), `atmega328p` (avrdude: part, flash + EEPROM),
  `esp32_4mb` (esptool: chip), `eeprom_24c02` (bp5_i2c, minipro). Проверка по схеме лезвия (новый `core/target.py`):
  опечатки, типы, размер образа лезвия (`Plugin.image_size`) против `size`; свойства переходника (`enabled`,
  `extra_args`, `programmer_voltage`, поля `safety: voltage`) в профиле запрещены. Ошибки — в капоте при проверке
  профиля и в самопроверке.
- **Выбор модели перед сеансом:** `Conductor.select(target, plugins, preflight)`; настройки лезвия =
  config.yaml < config.tools.yaml < `profile.tool[лезвие]`. Параметр `target` у `run`, `detect`, `params`, `tune`
  (методы ядра, действия Штурмана, CLI `--target`). Если лезвие переходника не узнаёт модель по ID
  (`Plugin.model_setting`: probe_rs, openocd, avrdude, bp5_i2c, minipro, modbus_rtu), Штурман спрашивает её списком
  профилей нужного класса; последний выбор — первым («в прошлый раз»), есть «Другая — как в настройках
  инструмента». Выбор дописывается в `data/choices.jsonl`. После опознания — «модель выбрана вами… проверьте по
  маркировке»; уверенность опознания прежняя.
- **«Подключить инструмент» начинается с переходника** (новый `workshop/connect.py`, действие Штурмана `connect`,
  `/api/connect`, страница в вебе, мастер, CLI `connect [id]`): программа установлена; правило udev
  `99-dirizher*.rules` на месте и знает VID:PID; пользователь в `plugdev`/`dialout`/`spi`; устройство видно по USB
  (`/sys/bus/usb/devices`); лезвие включено и настроено (или модель придёт из профиля) → «Настроить» →
  «Проверить подключение». Только чтение. Поля карточки переходника `groups:` и `preflight:`; у `usb_uart` — VID:PID
  CH340 и CP2102.
- **Опрос только нужных лезвий:** с выбранным переходником `detect` зовёт только его лезвия (остальные — «не
  опрашивается: выбран переходник …»); «что дальше» сохраняет переходник и модель.
- **Подготовка по переходнику:** строки шага 1 — из карточки (`preflight:`), иначе из лезвия (`Plugin.preflight`:
  SWD, ISP, UART, Bus Pirate, T48, Modbus), иначе прежний общий текст (у flashrom и симулятора — как было).
  У ESP больше нет слов о прищепке.
- Демо: список переходников записан, проверки — «только на приборе».
- 25 тестов (`tests/test_target.py`); прежние не менялись. Ядро: `core/target.py` (новый), `plugin.py`
  (`model_setting`, `size_setting`, `preflight`, `image_size`), `profiles.py` (`tool`), `registry.py` (`overlay`,
  `only`), `pipeline.py` (`select`, `preflight_lines`, `target=` у сценариев).

### S3. `inspect()` и замер напряжения (2026-11-25)
- **`Plugin.inspect(det)`** — только чтение, по умолчанию пусто. Возвращает `Inspection` (`core/models.py`:
  `findings`, `measured_voltage`) или список `Finding`. Ядро (`Conductor.inspect`) зовёт её после опознания, до шага
  «Напряжение» — в `run`, `rollback`, `params`, `tune` (в `detect` — нет: там только опознание). Находки
  показываются и пишутся в журнал (`[статус] проверка: текст`); «block» запрещает запись (`write_blockers`), как
  диагностика. Замечания inspect («warn») — сведения об устройстве: исправную прошивку они не делают «нет способа
  ремонта». Ошибка inspect сеанс не роняет (строка «info»). В отпечаток ничего не входит.
- **Замер в шаге 3** (`Safety.measured_check`): если лезвие дало `measured_voltage`, оно сверяется с напряжением
  профиля и адаптера (допуск `voltage_tolerance`): «замерено 1,8 В, а профиль на 3,3 В» — стоп; меньше 0,5 В —
  «на цели нет питания». Замер только добавляет: прежний запрет остаётся запретом, вопрос «проверили по даташиту?»
  при профиле без напряжения задаётся как раньше; нет замера — всё как раньше. У лезвий без проверки напряжения
  (RS-485) замер не используется.
- **Что открыто у лезвий** (каждое — с подставной программой, форматы помечены `ПРОВЕРИТЬ НА ЖЕЛЕЗЕ`):
  - flashrom: `--wp-status` (с версии 1.3) — защита записи, область и режим; объясняет «записалось, но не изменилось»;
    версия flashrom спрашивается один раз за сеанс;
  - OpenOCD: замер «Target voltage» (раньше шёл только в описание) → в шаг 3; защита чтения командой `rdp_cmd`
    (только `…_read`, `flash info`, `mdw`; у STM32F103C8 в профиле — `stm32f1x options_read 0`); новое поле
    `measure_voltage` (выключить замер у клона с неверным числом; только в настройках переходника — в профиле запрещено);
  - probe-rs: регистр ID из профиля (`id_register`: у STM32F103C8 — DBGMCU_IDCODE, DEV_ID 0x410) — подтверждает
    выбранную модель; не совпал — запись запрещена;
  - avrdude: фьюзы и lock-биты (`-n -U lfuse:r:-:h …`, только «:r:», проверяется перед запуском) и расшифровка по
    профилю (`fuses:`, новый `core/fuses.py`): у ATmega328P — тактирование, CKDIV8, RESET, debugWIRE, EESAVE,
    загрузчик, BOD, защита; «чтение запрещено» — запись запрещена. Фьюзы по-прежнему не пишутся;
  - esptool: MAC и ID флеша; если установлен `espefuse` — `summary`: шифрование флеша, secure boot (только сводка);
  - minipro: проверка контакта выводов `-z` (если есть в `--help`); плохой контакт — запись запрещена;
  - Bus Pirate 5: замер на VOUT из ответа `W <В>` (помощник печатает `VOUT=…`) → в шаг 3.
- Профиль: новые необязательные поля `fuses:` и `id_register:` (проверяются при загрузке), заполнены у atmega328p и
  stm32f103c8; образец — в `profiles/chips/_template.yaml`.
- Карточки движков (flashrom, OpenOCD, probe-rs, avrdude, esptool, minipro, Bus Pirate): в «Как работает в Дирижёре» —
  что Дирижёр берёт у программы для диагностики.
- Подставные программы: `--wp-status` у flashrom, `b32` у probe-rs, `options_read` и напряжение у OpenOCD, фьюзы у
  avrdude, `--help`/`-z` у minipro, новый `espefuse`; эмулятор BP5 умеет «просевший» VOUT.
- 36 тестов (`tests/test_inspect.py`), всего 306. Поправлены два прежних теста, смысл прежний: avrdude «никогда не
  трогает фьюзы» — теперь фьюзы читаются (только «:r:» и с -n), пишутся по-прежнему лишь flash и eeprom; probe-rs
  «дамп не сохраняется» — проверяются чтения `b8` (дамп), а вывод `b32` регистра ID сохраняется для сверки формата.
- Ядро: `models.py` (`Inspection`), `plugin.py` (`inspect`), `pipeline.py` (`Conductor.inspect`, замер в
  `_voltage_gate`), `safety.py` (`measured_check`), `profiles.py` (`fuses`, `id_register`), новый `fuses.py`.

### S4a. Карта разделов и частичное восстановление (2026-11-25)
- **`core/layout.py`** (по образцу `core/params.py`): поле профиля `layout:` — разделы `id`, `title`, `offset`,
  `length` или `end`, `kind` (boot, kernel, rootfs, config, calibration, unique, data, free), `preserve`, `restore`,
  `help`. Проверка при загрузке: без пересечений, в пределах `size`, ровно один из `length`/`end`, без лишних полей,
  `preserve` и `restore` вместе нельзя. По умолчанию `preserve` — у `unique`; `restore` — у boot, kernel, rootfs,
  data, free (настройки, калибровки и уникальное из эталона берутся только по явному `restore: true`).
- `preserve` профиля дополняется разделами с `preserve: true` (одинаковые области не дублируются); старое поле — как было.
- **Диагностика по разделам:** `compare_reference` дописывает «По разделам: «Прошивка» — 157 секторов, «Параметры» —
  1 сектор.» (начало сообщения прежнее); уникальное не считается отличием, отличия вне разделов — «вне карты».
  Новая проверка `layout` (у профиля с картой добавляется сама): пустой раздел загрузчика (весь 0xFF или 0x00) — «fail».
  Разделы с отличиями пишутся в журнал сеанса (событие с `regions`).
- **Рецепт `restore_regions`** — новое действие ядра `write_reference_regions` (`Conductor._build_regions`): образ =
  текущий чип, а отличающиеся разделы с `restore: true` — из эталона; уникальное, настройки и место вне карты не
  трогаются, план перечисляет «беру из эталона: …» и «не трогаю …». Запись — прежним путём: копия «до», план,
  `write_blockers`, слово «ДА», `apply()` (сверка всего чипа, копия «после»), при неудаче — возврат «до».
  Рецепт без `layout` — ошибка профиля. Предлагается `compare_reference` и `layout`, вторым после `restore_reference`.
- Учебная плата `example_sim_board`: карта из 5 разделов (заголовок, прошивка, свободное место, параметры, MAC и
  серийник) и рецепт `restore_regions`. Тренажёр («сеанс вживую» сбоя обновления) и демо показывают разделы и выбор способа.
- Веб и мастер: в подробностях сеанса — «Разделы с отличиями от эталона» (`guide.session_detail` → `regions`).
- Справка `help/layout.md`; образец карты и рецепта — в `profiles/boards/_template_board.yaml`.
- 12 тестов (`tests/test_layout.py`), всего 318. Прежние тесты сбоя обновления на учебной плате теперь отвечают на
  новый вопрос «Что сделать?» (выбор из двух способов) первым вариантом — смысл прежний (полный эталон):
  `test_pipeline` (4), `test_interface` (веб 2, мастер 1, Штурман 1), `test_playground` (ответы ядру), `test_catalog`
  (демо: выбор, затем слово «ДА»); в `tools/build_pages.py` — ответ «0» в основном ходе.

### S4b. Разделы сами: таблица ESP, Intel IFD, черновик платы (2026-11-25)
- **`core/layout_detect.py`** — определители разметки (регистрация `@register(имя, название)`, как у проверок),
  только stdlib. По копии «до» строят карту разделов в формате поля `layout:` и проверяют её тем же
  `layout.normalize`. Ничего не пишут; исключение разборщика — находка, а не падение.
  - `esp_partitions` — таблица разделов ESP-IDF с 0x8000: записи по 32 байта (`AA 50`, тип, подтип, смещение,
    размер, метка, флаги), запись MD5 `EB EB` проверяется, конец — 0xFF. Загрузчик (0x1000 у классического ESP32,
    0x0 у S3/C3 — по байту `E9`) и сама таблица — `boot`; приложения — `app`; `nvs`, `phy_init`, `nvs_keys`,
    `efuse` — `preserve`; `otadata` — `config`; FAT/SPIFFS/LittleFS — `rootfs` без `restore` (файлы владельца).
  - `intel_ifd` — Intel Flash Descriptor: подпись `5A A5 F0 0F` на 0x10, FLMAP0 → FRBA → регистры FLREGn
    (база/предел по 4 КБ, пустые пропускаются): Descriptor, BIOS, ME, GbE (MAC — `preserve`), Platform Data, EC и др.
  - Испорченная таблица (MD5, запись без подписи, раздел за краем флеша, пересечения, нет дескриптора, FLMAP0) —
    находка `layout_auto` «fail»: «подпись есть, но разметка испорчена — …», сеанс идёт без карты.
- Поле профиля **`layout_auto`** (`[esp_partitions, intel_ifd]` или `all`); неизвестное имя — ошибка профиля.
  Рецепт `restore_regions` допустим и при `layout_auto` (без найденной карты он не предлагается — подсказка в плане).
  `layout_auto: all` — у `generic_spi_nor`, `winbond_w25q64`, `winbond_w25q64fw`, `macronix_mx25l6406`;
  `[esp_partitions]` — у `esp32_4mb` (и рецепт `restore_regions`; пометка «добавьте preserve вручную» снята) и `generic_esp`.
- **Сценарий `run`:** в шаге 5 до поиска эталона `Conductor.auto_layout` — карта из профиля главнее; найденная
  подставляется в профиль сеанса (копия, база не меняется), `preserve` дополняется её уникальными разделами.
  Находка «ok» перечисляет разделы и что сохраняется с чипа; событие журнала с `layout_auto`.
- **Сверка карты с эталоном** (`Conductor.auto_layout_reference`): карта из чипа может быть испорчена (у дескриптора
  Intel нет контрольной суммы), поэтому при эталоне тот же определитель разбирает и его. Совпало — как было; не совпало
  или в эталоне не найдено — находка «warn» «разметка на чипе и в эталоне различается — частичное восстановление не
  предлагаю»: карты в сеансе нет, `restore_regions` в план не попадает (полная запись эталона остаётся), уникальные
  области — по разметке эталона, если она есть, иначе с чипа.
- **Черновик профиля платы** при сохранении эталона (`_offer_reference`, `reference`, после успешного ремонта), если
  профиль — не профиль платы: `data/drafts/board_<профиль>_<sha8>.yaml` — `content_match` (первые непустые 16 байт
  вне уникальных областей), `layout` и рецепт `restore_regions`, если карта найдена, `binwalk_expect` из сигнатур
  binwalk, если он установлен (`learning.record_board`). Готовый черновик не переписывается.
- Новый `kind: app` — «приложение (прошивка)», из эталона по умолчанию берётся.
- Веб и мастер: в подробностях сеанса — «Разделы по содержимому» (`guide.session_detail` → `auto_layout`).
- Справка `help/layout.md` — раздел «Разделы сами».
- 24 теста (`tests/test_layout_detect.py`, в т. ч. IFD с испорченным регионом GbE на чипе), всего 342. Подставной образ ESP (`tests/fakes/fake_tools.healthy_esp`)
